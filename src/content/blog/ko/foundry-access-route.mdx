[개념 지도](../foundry-concept-map/) 글은 Foundry의 주요 개념 31개를 지도 한 장에 담았습니다.\

그래서 질문 하나에 답하는 개념끼리 노선으로 묶고 노선마다 자세한 설명과 쓰임새를 따로 정리하기로 했습니다.\
이 글은 그 첫 번째로 권한 노선을 다룹니다.

Foundry에서 "이 사용자가 이 데이터를 볼 수 있는가"는 한 곳에서 정해지지 않습니다.\
리소스 전체에 걸리는 Project 권한과 Marking, Dataset의 행을 거르는 Restricted view, Ontology의 Object를 거르는 Object security policy가 함께 적용됩니다.\
Action으로 하는 수정은 Submission criteria(제출 조건)가 한 번 더 거르고 외부 앱은 요청 scope와 (제한된 앱이면) 앱 제한이 범위를 다시 좁힙니다.

이 글은 [개념 지도](../foundry-concept-map/#route-access)의 권한 노선을 따라 단계마다 무엇을 막는지 설명합니다.\
이어서 비슷해 보이는 장치 중 언제 무엇을 쓰는지와 한 곳을 막아도 열려 있는 곳을 정리합니다.

## 노선 지도

아래 지도는 권한 노선이 켜진 상태로 열립니다.\
번호는 이 글에서 다루는 순서이고 상자나 이름을 누르면 그 개념의 요약 카드가 표시됩니다.\
"전체"를 누르면 개념 지도 전체를 볼 수 있습니다.

## 1. Project · Role · Marking: 모든 리소스의 기본 관문

Foundry는 필수 통제(mandatory control)와 임의 통제(discretionary control)를 함께 써서 누가 어떤 데이터를 다룰 수 있는지 정합니다([Project · Role · Marking](#concept-project)).\
Project Role은 임의 통제이며 Project는 Role 부여의 기본 경계입니다.\
Role은 사용자나 그룹에 부여하며 공식 문서는 Project 단위로 그룹에 부여하도록 권장합니다.\
Project 안의 리소스는 그 Role을 물려받습니다.\
기본 Role은 권한이 큰 순서로 Owner, Editor, Viewer, Discoverer입니다.

Marking, Organization, Classification-based Access Controls(CBAC)는 필수 통제입니다.\
필수 통제는 Role과 관계없이 자격이 없는 사용자의 접근을 막습니다.\
Marking 하나에 대한 접근은 all-or-nothing입니다.\
여러 Marking은 AND 조건이라서 파일·폴더·Project에 붙은 Marking 모두의 멤버여야 접근할 수 있습니다.\
Marking은 파일 계층과 데이터 의존 관계를 따라 상속되며 명시적으로 제거하지 않는 한 파생 리소스에도 붙습니다.\
다만 Action은 쓰는 데이터의 보안을 Action의 로직이 정하므로 Action이 쓴 결과에는 읽은 데이터의 Marking이 따라가지 않을 수 있습니다(아래 "파생 데이터까지 막을 때"에서 설명합니다).\
Marking을 제거하려면 그 Marking의 Expand Access 권한이 필요하며 Dataset의 Owner Role만으로는 제거할 수 없습니다.\
공식 문서는 Marking을 접근 제한에만 쓰고 접근 권한은 Project의 Role로 부여하도록 안내합니다.

Object type·Link type·Action type 같은 Ontology 리소스도 Project에 저장하고 Project Role로 권한을 관리합니다.\
이 방식은 레거시 모델인 ontology roles와 datasource-derived 권한 모델을 대체하며 새 Ontology에는 기본으로 켜져 있습니다.\
기존 Ontology는 Ontology의 Owner가 이 기능을 직접 켜야 하고 기존 리소스는 migration이 필요합니다.\
project-based 권한으로 migration한 리소스는 예전 권한 모델로 되돌릴 수 없습니다.\
Object를 보려면 Object type의 Viewer 권한과 데이터 접근 권한이 함께 필요합니다.\
데이터 접근은 Object type 설정에 따라 Object security policy·Property security policy나 backing datasource의 권한으로 정해집니다.

공식 문서: [Projects and roles](https://www.palantir.com/docs/foundry/security/projects-and-roles) · [Markings](https://www.palantir.com/docs/foundry/security/markings) · [Ontology permissions](https://www.palantir.com/docs/foundry/object-permissioning/ontology-permissions) · [project-based 권한으로 migration](https://www.palantir.com/docs/foundry/ontology-manager/migrate-to-project-based-permissions)

## 2. Restricted view: Dataset의 행 단위 통제

[Restricted view](#concept-rv)는 backing Dataset 위에 만들어 사용자가 볼 권한이 있는 행만 보이게 합니다.\
정책은 granular policy로 작성합니다.\
granular policy는 사용자 속성과 컬럼과 값을 비교하는 규칙과 논리 연산자로 구성됩니다.\
정책에서 사용자·그룹·Organization을 가리킬 때는 이름이 아니라 UUID를 씁니다.\
그룹·Marking·Organization 멤버십에 NOT 조건을 쓰는 것은 피해야 합니다.\
범위가 좁혀진 토큰(scoped token)에는 검사할 속성이 없을 수 있어서 조건이 통과되고 필요 이상으로 접근이 열릴 수 있기 때문입니다.

Owner Role이나 필요한 권한이 있는 사용자가 Dataset을 우클릭해 만듭니다.\
만들면 입력 Dataset이 갱신될 때마다 다시 Build하는 Schedule이 자동으로 생깁니다.\
정책을 바꾸면 파이프라인을 다시 Build해야 읽기에 반영됩니다.\
Restricted view는 Dataset에만 만들 수 있고 Stream 같은 다른 datasource에는 만들 수 없습니다.\
새 Dataset을 만드는 transform 같은 배치 작업의 입력으로도 쓸 수 없습니다.\
Restricted view를 datasource로 쓰는 Object type에서는 특정 Object에 접근할 수 있는지가 그 행에 접근할 수 있는지로 정해집니다.

Restricted view는 backing Dataset 자체를 잠그지 않습니다.\
Restricted view로만 데이터를 봐야 하는 사용자에게는 backing Dataset 권한을 주지 않아야 합니다.\
공식 문서에 따르면 Restricted view는 보통 backing Dataset과 다른 Project에 저장합니다.\
같은 Project에 둘 때는 Marking으로 backing Dataset을 보호합니다.\
Restricted view는 backing Dataset의 Marking을 물려받으며 Marking 권한이 있으면 만들 때 물려받은 Marking을 뺄 수 있습니다.\
그러나 granular policy는 사용자가 읽는 순간에만 적용됩니다.\
파생 데이터로 전파되어 하류를 보호하는 것은 Marking입니다.\
그래서 공식 문서는 granular policy가 이미 접근을 통제한다는 이유로 물려받은 Marking을 빼지 말라고 안내합니다.\
Marking은 모두 통과해야 하는 조건이라서 Restricted view를 읽는 사용자도 Restricted view에 남은 Marking의 멤버여야 합니다.\
그래서 같은 Project에서 backing Dataset을 막으려고 건 Marking이 Restricted view에 그대로 남으면 그 Marking으로는 Restricted view 사용자가 backing Dataset을 직접 읽는 것을 막지 못합니다.\
물려받은 Marking을 그대로 두면서 backing Dataset을 막으려면 Restricted view를 다른 Project에 두고 Restricted view 사용자에게 backing Dataset이 든 Project의 Role이나 backing Dataset 자체의 권한을 주지 않습니다.

공식 문서: [Restricted views](https://www.palantir.com/docs/foundry/security/restricted-views) · [Managing object security](https://www.palantir.com/docs/foundry/object-permissioning/managing-object-security) · [Manage granular policies](https://www.palantir.com/docs/foundry/platform-security-management/manage-granular-policies) · [Markings](https://www.palantir.com/docs/foundry/security/markings) · [Restricted view 기반 Object type 설정](https://www.palantir.com/docs/foundry/object-permissioning/configuring-rv-access-controls)

## 3. Object security policy: Ontology 안의 행·셀 단위 통제

[Object security policy](#concept-osp)는 Object type에 설정해 사용자가 볼 수 있는 Object를 행 단위로 거릅니다.\
Property security policy는 지정한 property만 거르는 열 단위 통제입니다.\
Object security policy와 함께 쓰면 셀 단위까지 제어할 수 있습니다.\
Object security policy는 통과했지만 Property security policy를 통과하지 못한 사용자에게는 그 property가 null로 보입니다.\
Property security policy를 만들려면 Object security policy가 먼저 있어야 합니다.\
primary key는 어떤 Property security policy에도 넣을 수 없고 다른 property는 Property security policy 하나에만 들어갈 수 있습니다.

정책이 있으면 Object를 보는 데 backing datasource의 Viewer 권한은 필요하지 않습니다.\
레거시 datasource-derived 권한 모델을 쓰는 환경에서는 정책이 있어도 backing datasource의 Viewer 권한이 필요합니다.\
Object security policy는 datasource의 필수 통제(Marking·Organization·CBAC)를 기본으로 물려받습니다.\
여기에 필수 통제를 더하거나 더는 필요 없는 것을 뺄 수 있습니다.\
정책 변경은 거의 즉시 반영되지만 그룹 멤버십 같은 사용자 속성의 변경은 잠시 캐시됩니다.

정책을 만들고 고치려면 Object type의 Owner여야 합니다.\
project-based 권한에서는 그 Object type이 든 Project의 Owner를 뜻하고 레거시 datasource-derived 권한 모델에서는 Ontology의 Owner를 뜻합니다.\
공식 문서는 정책을 설정하기 전에 project-based 권한으로 migration하도록 권장합니다.\
Restricted view 정책과 마찬가지로 그룹·Marking·Organization 멤버십에 NOT 조건을 쓰는 것은 피해야 합니다.

공식 문서: [Object security policies](https://www.palantir.com/docs/foundry/object-permissioning/object-security-policies) · [Managing object security](https://www.palantir.com/docs/foundry/object-permissioning/managing-object-security)

## 4. Action type: 고치려면 Submission criteria도 통과해야 합니다

[Action](#concept-action)을 제출하려면 Submission criteria를 통과해야 합니다.\
Submission criteria의 조건은 세 가지 틀로 만듭니다.\
제출하는 사용자(사용자 ID, 그룹 멤버십, Multipass의 사용자 속성)와 파라미터 값(Object 파라미터면 그 property 값)과 실행 맥락(Ontology Scenario 안에서 제출했는지)입니다.\
사용자 조건에서도 Restricted view 정책과 마찬가지로 그룹·Marking·Organization 멤버십에 NOT 조건을 쓰는 것은 피해야 합니다.\
제출하는 사용자는 Submission criteria와 별개로 편집 대상 Object type·Link type과 그 datasource도 볼 수 있어야 합니다.

새 Object type의 기본값은 Action으로만 편집하는 방식입니다.\
이 방식에서는 볼 수 있는 Object를 모두 편집할 수 있고 편집할 Object에 필요한 것은 Read 권한뿐입니다.\
공식 문서는 그래서 사용자가 자신이 볼 수 없는 Object를 만들 수도 있다고 설명합니다.

Restricted view 기반 Object type에서는 보안 정책이 참조하는 property를 Action으로 고치면 그 Object를 볼 수 있는 사용자가 바뀝니다.\
Restricted view의 행은 Action 편집의 영향을 받지 않으므로 Ontology에서 Object를 볼 수 있는 사용자와 Restricted view에서 그 행을 볼 수 있는 사용자가 달라질 수 있습니다.

Action 밖 편집(Foundry Forms, Object Explorer 직접 편집, API 호출)도 허용한 Object type·Link type은 backing 종류에 따라 조건이 더 붙습니다.\
Dataset 기반이면 writeback Dataset의 Edit 권한이 추가로 필요합니다.\
Restricted view 기반이면 edit policy를 통과해야 합니다.\
이 edit policy는 Object Storage v1을 쓰고 Action으로만 편집하도록 설정하지 않은 Object type에서만 Ontology Manager의 Datasources 탭에서 설정할 수 있습니다.\
공식 문서는 Object Storage v1이 2026년 6월 30일 이후 제공되지 않는다고 안내합니다.\
그 밖의 Restricted view 기반 Object type은 그 Object type을 편집하는 Action type으로 편집 권한을 통제합니다.\
Edit 권한이 있으면 writeback Dataset의 데이터를 모두 볼 수 있어서 편집에 필요한 것보다 많은 데이터가 드러날 수 있으므로 공식 문서는 Action 밖 편집을 허용하는 설정을 권장하지 않습니다.

Action type에 action log가 설정되어 있으면 제출하는 사용자에게 action log Object type에 대한 권한도 필요하며 Action이 만들거나 고치는 다른 Object type도 마찬가지입니다.\
이 권한이 없으면 제출 시점에 실패합니다.

공식 문서: [Action type permissions](https://www.palantir.com/docs/foundry/action-types/permissions) · [Submission criteria](https://www.palantir.com/docs/foundry/action-types/submission-criteria) · [Restricted view 기반 Object type 설정](https://www.palantir.com/docs/foundry/object-permissioning/configuring-rv-access-controls) · [편집이 적용되는 방식](https://www.palantir.com/docs/foundry/object-edits/how-edits-applied)

## 5. OAuth: 외부 앱이 받는 토큰의 범위

OSDK(Ontology SDK)로 만든 외부 앱은 [Developer Console](#concept-osdk)에 등록하고 [OAuth](#concept-oauth)로 토큰을 받습니다.\
Authorization code 방식은 사용자를 대신해 동작하고 Client credentials 방식은 서비스 유저로 동작합니다.\
Developer Console에서 앱의 권한 방식으로 Application permissions를 고르면 앱은 자체 서비스 유저로 동작하므로 로그인한 사용자의 권한과 관계없이 서비스 유저가 볼 수 있는 데이터를 보여 줄 수 있습니다.\
토큰이 접근할 수 있는 범위는 아래 셋이 모두 허용하는 교집합입니다.

- 사용자(Authorization code) 또는 서비스 유저(Client credentials)의 Foundry 권한
- Developer Console에 설정한 앱 제한(application restrictions)
- 토큰을 요청할 때 고른 작업(operation) scope

앱 제한에는 접근할 리소스를 정하는 resource restrictions와 할 수 있는 작업을 정하는 operation restrictions가 있습니다.\
토큰을 요청할 때 좁힐 수 있는 것은 작업뿐입니다.\
리소스 접근은 앱의 resource restrictions와 사용자 권한만으로 정해집니다.\
예를 들어 사용자가 주문·고객·재고를 모두 볼 수 있어도 앱의 resource restrictions에 고객이 없으면 토큰은 고객에 접근할 수 없습니다.

| 범위 | 주문 | 고객 | 재고 |
| --- | :-: | :-: | :-: |
| 사용자(또는 서비스 유저) 권한 | ✓ | ✓ | ✓ |
| 앱 제한 (resource restrictions) | ✓ | ✗ | ✓ |
| **토큰 리소스 접근 범위** | **✓** | ✗ | **✓** |

표는 리소스 범위만 나타냅니다.\
제한된 앱에서 OSDK로 쓰는 Object type·Action type 같은 Ontology 리소스는 Developer Console의 Ontology SDK 탭에서 resource restrictions에 추가합니다.\
Platform SDK로 Dataset 같은 리소스를 읽으려면 그 리소스가 든 Project를 Platform SDK 탭에서 resource restrictions에 넣고 필요한 작업(예: `api:use-datasets-read`)도 operation restrictions에 넣어야 합니다.

앱은 기본적으로 제한(restricted) 상태로 만들어집니다.\
제한 없는(unrestricted) 앱은 사용자 권한과 요청한 작업만으로 접근이 정해지므로 신뢰할 수 있는 코드에만 써야 합니다.\
제한된 앱에서 scope를 빈 값(`[]`)으로 요청하면 앱의 operation restrictions가 적용되고 scope 없이 요청하면 앱 제한이 허용하는 사용자 권한 전부가 적용됩니다.\
제한 없는 앱이 Authorization code 방식을 쓰면 scope를 반드시 요청해야 합니다.\
제한 없는 앱이 Client credentials 방식으로 scope 없이 요청하면 서비스 유저가 할 수 있는 작업이 모두 허용됩니다.\
Global Branching의 브랜치에서 앱을 개발해도 앱 제한은 Main을 포함한 모든 브랜치가 함께 씁니다.\
브랜치에서는 필요한 Ontology 리소스를 resource restrictions에 넣는 것만 할 수 있고 이 변경은 Main을 포함한 모든 브랜치에서 앱이 허용받는 최대 범위에 함께 들어갑니다.\
필요 없어진 리소스는 Main에서 Review resources로 정리합니다.\
다른 SDK 버전이나 브랜치가 아직 쓰는 리소스를 지우면 그 브랜치의 앱이 깨질 수 있습니다.

공식 문서: [Application restrictions](https://www.palantir.com/docs/foundry/developer-console/application-restrictions) · [Developer Console 권한](https://www.palantir.com/docs/foundry/developer-console/permissions) · [Developer Console 브랜치](https://www.palantir.com/docs/foundry/developer-console/branching-integration) · [OAuth 클라이언트 작성](https://www.palantir.com/docs/foundry/platform-security-third-party/writing-oauth2-clients)

## 6. Approvals · Checkpoints: 권한이 없을 때와 민감한 작업 전

어떤 변경을 할 권한이 없는 사용자는 그 변경을 request로 요청하고 request는 승인할 관리자에게 전달됩니다.\
이 요청과 승인과 적용의 흐름을 [Approvals](#concept-approvals)에서 다룹니다.\
request는 하나 이상의 task로 구성되고 task마다 승인할 수 있는 검토자가 정해져 있습니다.\
task의 예로는 그룹 멤버십, Project 접근, Marking 접근, Project 참조 추가, Ontology proposal이 있습니다.\
Marking 접근은 그 Marking에 Manage permissions가 있는 관리자가 승인합니다.\
그룹이 지정되지 않은 Project에 Project 접근을 요청하면 그 Project의 Owner가 승인합니다.\
Foundry 안에서 관리하는 그룹에 가입하는 방식으로 요청하면 그 그룹의 관리자가 승인합니다.\
모든 task가 승인되면 request가 적용(invoke)됩니다.\
다만 필수 checkpoint를 아직 제출하지 않았으면 제출할 때까지 적용되지 않습니다(Action required 상태).

Checkpoints는 민감할 수 있는 작업을 멈추고 사용자에게 사유를 묻는 데이터 거버넌스 도구입니다.\
Foundry의 60개가 넘는 상호작용에 통합되어 있습니다.\
사유는 시각·사용자·관련 리소스와 함께 기록되고 관리자가 Checkpoints 앱에서 검토합니다.

공식 문서: [Approvals](https://www.palantir.com/docs/foundry/approvals/overview) · [Checkpoints](https://www.palantir.com/docs/foundry/checkpoints/overview) · [Projects and roles](https://www.palantir.com/docs/foundry/security/projects-and-roles)

## 언제 무엇을 쓰나

### 행을 거를 때: Object security policy와 Restricted view

| 기준 | Object security policy | Restricted view |
| --- | --- | --- |
| 거르는 대상 | Ontology의 Object.<br />Property security policy와 함께 쓰면 셀 단위까지 | Dataset의 행과 그 행으로 만든 Object.<br />multi-datasource Object type과 함께 쓰면 셀 단위까지 |
| 정책 변경 반영 | 거의 즉시 | 파이프라인을 다시 Build해야 반영 |
| Stream 기반 Object type | 적용할 수 있음 | 만들 수 없음(Dataset에만) |
| Ontology 밖(예: Code Workspaces)의 Dataset 읽기 | 보호하지 않음(Ontology 안에서만 적용) | Restricted view로 읽을 때 보호함.<br />backing Dataset 권한은 주지 않아야 함 |
| 파생 데이터로 전파 | 행·열 거르기는 전파되지 않음.<br />정책에 넣은 필수 통제는 파생 데이터에도 적용 | 행 거르기는 전파되지 않음 |

공식 문서는 Ontology에서 Object 보안을 관리할 때 대부분의 경우 Object security policy와 Property security policy를 권장합니다.\
Restricted view는 backing Dataset을 Ontology 밖에서도 사용자별로 행 단위 보호해야 할 때 맞습니다.\
datasource마다 다른 resolution strategy나 build schedule 때문에 multi-datasource Object type을 써야 하면 datasource 쪽 정책이 필요할 수 있습니다.\
datasource 권한으로 접근을 정하는 Object type에서는 Stream의 Viewer 권한이 있으면 그 Stream으로 만든 Object를 모두 볼 수 있습니다.\
Restricted view는 Stream에 만들 수 없으므로 Stream 기반 Object type을 행 단위로 나누려면 Object security policy를 씁니다.

공식 문서: [Managing object security](https://www.palantir.com/docs/foundry/object-permissioning/managing-object-security) · [Restricted views](https://www.palantir.com/docs/foundry/security/restricted-views)

### 권한을 줄 때와 막을 때: Role과 Marking

| 기준 | Role | Marking |
| --- | --- | --- |
| 종류 | 임의 통제(discretionary) | 필수 통제(mandatory) |
| 하는 일 | 할 수 있는 일을 부여 | 자격이 없는 사용자를 차단.<br />접근 부여에는 쓰지 않도록 안내(Role로 부여) |
| 붙는 곳 | 보통 Project 단위로 사용자나 그룹에 | 파일·폴더·Project |
| 파생 데이터 | 따라가지 않음 | 명시적으로 제거하지 않는 한 따라감.<br />Action이 쓴 결과는 예외일 수 있음 |

공식 문서: [Projects and roles](https://www.palantir.com/docs/foundry/security/projects-and-roles) · [Markings](https://www.palantir.com/docs/foundry/security/markings) · [Read and write authorizations](https://www.palantir.com/docs/foundry/action-types/read-write-authorizations)

### 파생 데이터까지 막을 때: 필수 통제를 함께 겁니다

Project Role, Restricted view, Object security policy, Property security policy는 사용자가 읽는 순간에만 데이터를 거릅니다.\
읽은 뒤의 데이터에는 원본 정책이 따라가지 않습니다.\
공식 문서가 드는 예는 아래와 같습니다.

- Function의 반환값
- Action 편집 (쓰기 대상의 통제가 적용됨)
- AIP Logic 도구 호출로 모델에 들어간 데이터
- OSDK 응답
- Pipeline Builder의 Ontology 출력 (출력 대상의 통제가 적용됨)
- writeback (writeback 대상의 통제가 적용됨)
- 내보내기와 다운로드

반면 필수 통제인 Marking, CBAC, Organization은 파생과 하류 사용을 거쳐도 데이터를 따라갑니다.\
그래서 파생 데이터·writeback·내보내기·모델 출력까지 보호해야 하면 필수 통제를 씁니다.\
사용자별로 거르면서 하류로 흘러가는 데이터도 보호해야 하면 공식 문서는 둘을 함께 쓰도록 안내합니다.\
Marking을 건 Dataset을 backing으로 하는 Restricted view는 물려받은 Marking을 그대로 두면 사용자별로 행을 거르면서 backing Dataset과 파생 데이터에 Marking을 남깁니다.\
공식 문서는 더 강하게 보호하려면 Restricted view의 backing Dataset에 Marking을 걸라고 합니다.

Action은 예외입니다.\
Action이 쓰는 데이터의 보안은 Action의 로직이 정하므로 Action은 읽은 데이터와 같거나 높거나 낮은 보안으로 결과를 쓸 수 있습니다.\
read authorization은 Action이 읽을 수 있는 Marking 데이터의 상한을 정하고 write authorization은 Action이 쓰는 데이터가 갖춰야 할 최소 보안을 정합니다.\
두 설정은 지금 선택 사항이라서 read authorization이 없으면 Action이 Marking이 붙은 데이터를 읽어 덜 제한된 곳에 쓸 수 있습니다.\
그래서 공식 문서는 Marking이 붙은 데이터를 읽을 수 있는 Action에는 read authorization을 설정하라고 안내합니다.\
read authorization을 설정해도 write authorization을 그보다 덜 제한적으로 두면 Action은 읽은 데이터보다 낮은 보안으로 결과를 쓸 수 있습니다.\
이때 Foundry는 Action type을 저장하거나 게시하는 사용자가 두 경계 사이에서 빠지는 필수 Marking을 모두 해제(declassify)할 권한이 있는지 확인하며 실행할 때는 다시 확인하지 않습니다.\
Access constraints를 켜면 두 설정이 모두 빈 상태로 시작하므로 read authorization과 함께 write authorization도 정합니다.\
read·write authorization은 베타 기능이라 환경(enrollment)에 따라 제공되지 않을 수 있습니다.\
write authorization은 action log와 edit history처럼 플랫폼이 관리하는 쓰기에는 적용되지 않으므로 그 보안은 write authorization보다 낮을 수 있습니다.\
action log에는 파라미터 값과 Object 파라미터의 property 값이 기록될 수 있으므로 action log Object type의 권한도 따로 확인합니다.

공식 문서: [Access control propagation](https://www.palantir.com/docs/foundry/security/access-control-propagation) · [Read and write authorizations](https://www.palantir.com/docs/foundry/action-types/read-write-authorizations) · [Action log](https://www.palantir.com/docs/foundry/action-types/action-log)

## 정리

- 접근 권한은 Role로 받고 Marking·Organization·CBAC 같은 필수 통제는 Role과 함께 적용되어 자격이 없는 사용자를 막습니다.\
  Role은 보통 Project 단위로 부여합니다.
- 공식 문서는 Object의 행과 셀을 거를 때 대부분의 경우 Object security policy와 Property security policy를 권장합니다.\
  Ontology 밖에서도 Dataset의 행을 보호해야 하면 Restricted view를 씁니다.
- 행 단위 정책은 읽는 순간에만 적용됩니다.\
  파생 데이터까지 보호하려면 Marking 같은 필수 통제를 함께 겁니다.\
  Action은 결과의 보안을 로직이 정하므로 Marking이 붙은 데이터를 읽는 Action에는 read authorization(베타)을 설정하고 write authorization을 그보다 낮게 두지 않습니다.
- Action으로 수정하려면 Submission criteria를 통과하고 편집 대상 Object type·Link type과 그 datasource를 볼 수 있어야 합니다.\
  외부 앱의 토큰은 사용자(또는 서비스 유저) 권한과 (제한된 앱이면) 앱 제한이 모두 허용하는 리소스에만 접근합니다.
