Palantir Foundry는 데이터 수집과 가공, 업무 모델링, 애플리케이션 개발, 권한 관리를 하나의 플랫폼에서 다룹니다.\
범위가 넓은 만큼 처음 접하면 Dataset, Ontology, Funnel, Action, Function, OSDK처럼 비슷해 보이는 이름이 한꺼번에 등장하고, 각각이 전체 구조의 어디에 놓이는지 파악하기 어렵습니다.

이 글은 Foundry의 주요 개념 17개를 **데이터가 흐르는 순서**로 배치한 개념 지도입니다.\
각 개념은 개발자에게 익숙한 React·MySQL·클라우드 서비스, 또는 일상과 업무의 장면에 빗대어 설명합니다.

## 전체 흐름

Foundry의 구성 요소는 크게 다섯 개의 층과 이를 감싸는 권한 체계로 나눌 수 있습니다.

1. **데이터**: 엑셀 같은 원본 파일을 Python transform이나 Pipeline Builder로 가공해 Dataset에 저장합니다.\
   파일은 Media set에 따로 보관합니다.
2. **온톨로지**: Funnel이 Dataset을 인덱싱해 Ontology를 만듭니다.\
   Ontology는 Dataset에 업무 의미(Object, Property, Link)를 부여한 계층이며, 앱은 이 계층을 읽고 씁니다.
3. **로직**: Action은 Ontology를 수정하고, Function은 조회와 계산을 담당합니다.\
   별도 런타임이 필요하면 Compute module을 씁니다.
4. **앱**: Workshop(로우코드)이나 OSDK 기반 React 앱이 로직 계층을 호출해 사용자에게 화면을 제공합니다.
5. **운영**: Ontology Manager, Global Branching, Marketplace는 특정 층에 속하지 않고 모든 층의 변경과 배포를 관리합니다.

이 전체를 Project·Role·Marking 권한 체계가 감싸고, Object security policy와 OAuth가 각 층의 접근을 세밀하게 제어합니다.

## 개념 지도

그림의 상자나 개념 목록의 이름을 누르면 해당 개념의 요약 카드가 표시됩니다.\
상자와 이름의 색은 개념이 속한 층을 나타냅니다.\
카드의 "비유로 보면"에서 개발자용과 일반용 비유 중 편한 쪽을 고를 수 있습니다.\
비유는 이해를 돕기 위한 근사치이며, 실제 동작의 세부 사항은 카드 하단의 공식 문서를 기준으로 봐야 합니다.

## 자주 혼동하는 지점

Foundry는 권한과 동작이 여러 계층에 나뉘어 있어서, 비슷해 보이는 설정이 실제로는 서로 다른 곳에서 결정되는 경우가 많습니다.\
아래는 그중 특히 혼동하기 쉬운 세 가지입니다.\
개념 이름을 누르면 개념 카드가 해당 개념으로 바뀝니다.

### 조회 · 제출 · 저장은 서로 다른 곳에서 결정됩니다

"사용자가 이 Object를 수정할 수 있는가"라는 질문은 실제로는 세 개의 독립된 질문으로 나뉩니다.

| 질문 | 결정하는 곳 | DB 비유 |
| --- | --- | --- |
| 누가 어떤 Object를 볼 수 있는가? | [Object security policy](#concept-osp) | 모든 SELECT에 자동으로 붙는 WHERE |
| 이 Action을 제출할 수 있는가? | [Submission criteria](#concept-action) | UPDATE 전에 실행되는 IF 검사 |
| 변경은 언제 실제로 저장되는가? | [Action이 실행될 때만](#concept-function) | COMMIT.<br />Edit function은 변경할 SQL을 만드는 데까지만 관여 |

### OSDK 토큰의 권한은 세 범위의 교집합입니다

OSDK로 만든 앱이 받는 토큰은 사용자 권한, 앱에 설정된 최대 scope, 앱이 요청한 scope 세 가지가 모두 허용하는 범위만 접근할 수 있습니다.

| 범위 | 주문 | 고객 | 재고 |
| --- | :-: | :-: | :-: |
| 사용자 권한 | ✓ | ✓ | ✓ |
| 앱 최대 scope | ✓ | ✗ | ✓ |
| 요청 scope | ✓ | ✓ | ✗ |
| **토큰 접근 범위** | **✓** | ✗ | ✗ |

요청 scope는 브라우저에서 실행되는 코드가 정하므로 신뢰할 수 있는 경계가 아닙니다.\
보안 경계로 믿을 수 있는 것은 Developer Console에 저장된 앱 최대 scope뿐입니다([OSDK](#concept-osdk)).

### 권한이 서로 연동되지 않는 곳

한 곳의 권한을 막았다고 해서 관련 데이터가 모두 보호되지는 않습니다.\
다음 조합은 각각 따로 설정해야 합니다.

- **[Object security policy](#concept-osp) ↔ Dataset 권한**: 양방향으로 분리되어 있습니다.\
  Object를 가려도 원본 Dataset은 따로 잠가야 합니다.
- **[Media set](#concept-media) 권한 ↔ Object 정책**: 서로 별개입니다.\
  Property를 볼 수 없는 사용자도 Media set에서 파일을 직접 가져올 수 있습니다.\
  또한 같은 경로로 덮어써도 이전 파일은 기본적으로 삭제되지 않고 media reference로 계속 접근할 수 있으므로, 민감한 파일을 교체할 때는 보존 정책을 함께 설정해야 합니다.
- **[OSDK](#concept-osdk) scope**: 앱 전체에 적용되는 상한일 뿐입니다.\
  사용자별 차등이나 "앱을 통해서만 접근" 같은 제약은 걸 수 없습니다.
- **[Compute module](#concept-cm) Application permissions**: 호출한 사용자와 관계없이 서비스 유저의 권한으로 고정되어 동작합니다.

## 정리

- Foundry의 데이터는 **원본 → Dataset → Ontology → 로직 → 앱** 순서로 흐르며, 앱은 Dataset이 아니라 Ontology를 다룹니다.
- 쓰기는 반드시 **Action**을 거칩니다.\
  Function은 계산하고 조회할 뿐 직접 저장하지 않습니다.
- 권한은 **계층마다 독립적**입니다.\
  Ontology의 Object 정책, 원본 Dataset, Media set, OSDK scope를 각각 따로 설계해야 합니다.
