처음으로 Palantir Foundry 프로젝트를 맡게 되었습니다.\
Foundry는 기존에 익숙하던 개발 환경과 용어도 개념도 다른 부분이 많았습니다.\

이를 풀기 위해 여러 AI 도구를 활용해 학습했고 그 과정에서 내용을 정리하다 보니 지금의 개념 지도 형태가 되었습니다.\
같은 고민을 하는 분들과 나누고 싶어 블로그 글로 옮겼습니다.

Palantir Foundry는 데이터 수집과 가공, 업무 모델링, 애플리케이션 개발, 권한 관리를 하나의 플랫폼에서 다룹니다.\
범위가 넓은 만큼 처음 접하면 Dataset, Ontology, Funnel, Action, Function, OSDK처럼 낯선 이름이 한꺼번에 등장하고 각각이 전체 구조의 어디에 놓이는지 파악하기 어렵습니다.

이 글은 Foundry의 주요 개념 31개를 **데이터가 흐르는 순서**로 배치한 개념 지도입니다.\
각 개념은 개발자에게 익숙한 React·MySQL·클라우드 서비스 또는 일상과 업무의 장면에 빗대어 설명합니다.

## 전체 흐름

Foundry의 구성 요소는 크게 데이터·온톨로지·로직·앱의 네 층, 여러 층에 걸쳐 쓰이는 운영 도구, 이 전체를 감싸는 권한 체계로 나눌 수 있습니다.

1. **데이터**: Data Connection으로 외부 시스템의 데이터를 가져오고 Python transform이나 Pipeline Builder로 가공해 Dataset에 저장합니다.\
   가공 작업은 Build로 실행되고 Schedule에 따라 반복됩니다.\
   파일은 스키마 없는 Dataset이나 Media set에 보관합니다.\
   지연이 짧아야 하는 데이터는 Dataset 대신 Stream으로 받아 Ontology에 초\~분 단위로 반영합니다.\
   외부 플랫폼의 테이블은 복사하지 않고 Virtual table로 등록해 바로 조회할 수 있습니다.\
   머신러닝 모델은 Models로 연결하고 Modeling Objectives에서 평가해 배포하거나 direct model deployment로 바로 배포합니다.
2. **온톨로지**: Funnel이 Dataset·Restricted view·Stream·Virtual table 같은 datasource의 데이터를 인덱싱해 Ontology의 Object로 만듭니다.\
   Ontology는 Dataset에 업무 의미(Object, Property, Link)를 부여한 계층이며 업무용 앱은 주로 이 계층을 읽고 씁니다.\
   Object type·Link type 같은 구조는 Ontology Manager에서 정의하며 Pipeline Builder도 Object type·Link type을 출력할 수 있습니다.\
   여러 Object type이 공유하는 공통 형태는 Interface로 정의합니다.
3. **로직**: Action은 Ontology를 수정하고 Function은 조회와 계산을 담당합니다.\
   직접 만든 컨테이너 코드는 Compute module로, 조건에 따른 자동 실행은 Automate로, LLM 기반 로직은 AIP Logic으로 만듭니다.
4. **앱**: Workshop(노코드)이나 OSDK 기반 React 앱은 Ontology를 직접 조회하고 쓰기는 Action으로 처리하며 복잡한 계산이 필요하면 Function 같은 로직 계층을 호출합니다.\
   Workshop은 Derived properties로 연결된 Object의 집계와 property 사이의 계산을 Ontology를 바꾸지 않고 화면에서 바로 하기도 합니다.\
   Contour · Quiver · Object Explorer로는 코드 없이 데이터를 분석합니다.\
   Object Views는 Object 하나의 정보를 모아 보여 주고 외부 AI 에이전트는 Ontology MCP로 Ontology를 읽고 Action을 실행합니다.
5. **운영**: Ontology Manager, Global Branching, Marketplace, Data Lineage · Workflow Lineage는 한 층에 속하지 않고 여러 층에 걸쳐 쓰이는 도구라서 지도에서는 맨 아래 운영 줄에 모았습니다.\
   Ontology Manager는 Ontology를 정의하고 Global Branching과 Marketplace는 지원 범위 안에서 여러 층의 변경과 배포를 관리합니다.\
   Data Lineage · Workflow Lineage로는 리소스 사이의 의존 관계를 확인합니다.\
   Project·Marking 접근 같은 권한 요청은 Approvals에서 승인하고 브랜치의 Ontology 변경은 Global Branching proposal과 함께 생기는 Ontology proposal에서 검토합니다.\
   Approvals · Checkpoints는 권한·보안 개념이지만 Ontology proposal로 Global Branching과 이어지므로 지도에서는 운영 줄에 함께 두었습니다.

이 전체를 Project · Role · Marking 권한 체계가 감쌉니다.\
여기에 더해 Restricted view는 Dataset의 행 단위 조회를, Object security policy와 Property security policy는 Ontology 안에서 Object·Property 단위의 조회를, OAuth는 외부 앱이 토큰을 받아 Foundry에 접근하는 과정을 담당합니다.

## 개념 지도

그림의 상자나 개념 목록의 이름을 누르면 해당 개념의 요약 카드가 표시됩니다.\
상자와 이름의 색은 개념이 속한 층을 나타냅니다.\
지도 위의 "관점으로 보기"에서 관점 하나를 고르면 그 관점의 질문이 나타나고 질문에 답하는 개념에 순서 번호가 붙으며 나머지 개념은 흐리게 표시됩니다.\
카드의 "비유로 보면"에서 개발자용과 일반용 비유 중 편한 쪽을 고를 수 있습니다.\
비유는 이해를 돕기 위한 근사치이며 실제 동작의 세부 사항은 카드 하단의 공식 문서를 기준으로 봐야 합니다.

## 자주 혼동하는 지점

Foundry는 권한과 동작이 여러 계층에 나뉘어 있어서 비슷해 보이는 설정이 실제로는 서로 다른 곳에서 결정되는 경우가 많습니다.\
아래는 그중 특히 혼동하기 쉬운 세 가지입니다.\
개념 이름을 누르면 개념 카드가 해당 개념으로 바뀝니다.

### 조회 · 제출 · 저장은 서로 다른 곳에서 결정됩니다

"사용자가 이 Object를 수정할 수 있는가"라는 질문은 실제로는 세 개의 독립된 질문으로 나뉩니다.

| 질문 | 결정하는 곳 | DB 비유 | 일상 비유 |
| --- | --- | --- | --- |
| 누가 어떤 Object를 볼 수 있는가? | Object type의 View 권한과 데이터 접근 권한이 함께 필요.<br />[Object security policy](#concept-osp)를 설정한 타입은 그 정책이 정하고(정책은 원본의 Marking 같은 필수 통제를 기본으로 물려받음) 설정하지 않은 타입은 backing datasource의 Viewer 권한이 필요.<br />레거시 datasource-derived 권한 모델에서는 정책이 있어도 backing datasource의 Viewer 권한이 필요.<br />Restricted view 기반 Object type은 Restricted view의 행 접근이 결정 | 모든 SELECT에 자동으로 붙는 WHERE | 같은 명부를 열어도 내 담당 줄만 보임 |
| 이 Action을 제출할 수 있는가? | [Submission criteria](#concept-action)를 통과하고 편집 대상 Object type·Link type과 그 datasource를 볼 권한이 필요.<br />Action 밖 편집도 허용한 타입은 writeback Dataset의 Edit 권한(Restricted view 기반이면 edit policy 통과)도 필요.<br />action log가 있으면 action log Object type 권한도 필요 | UPDATE 전에 실행되는 IF 검사 | 결재 조건을 통과해야 신청서를 낼 수 있음 |
| 변경은 언제 실제로 저장되는가? | 보통 [Action](#concept-action)이 실행될 때.<br />Action 밖 편집을 허용한 타입과 Automate의 Logic effect([AIP Logic](#concept-aip) 함수가 반환한 편집을 Action 없이 적용)는 예외 | COMMIT.<br />[Edit function](#concept-function)은 변경할 SQL을 만드는 데까지만 관여 | 신청서가 처리되어야 반영됨.<br />계산기로 미리 계산해 둔 것만으로는 반영되지 않음 |

공식 문서: [Ontology permissions](https://www.palantir.com/docs/foundry/object-permissioning/ontology-permissions) · [Object security policies](https://www.palantir.com/docs/foundry/object-permissioning/object-security-policies) · [Action type permissions](https://www.palantir.com/docs/foundry/action-types/permissions) · [Ontology edits](https://www.palantir.com/docs/foundry/functions/edits-overview) · [Logic effect](https://www.palantir.com/docs/foundry/automate/effect-logic)

### 편집은 원본 Dataset으로 돌아가지 않습니다

지도의 Materialization 화살표는 원본 Dataset과 Object type 사이의 양방향 동기화가 아닙니다.\
Action 편집은 원본(backing) Dataset에 쓰이지 않고 아래 표처럼 따로 저장됩니다.

| 저장되는 곳 | 담기는 내용 | 갱신 시점 | 만드는 주체 |
| --- | --- | --- | --- |
| 원본(backing) [Dataset](#concept-dataset) | 파이프라인이 만든 데이터.<br />Action 편집은 들어가지 않음 | 파이프라인의 Build | 데이터 파이프라인 |
| Object Storage v2(OSv2)의 [Ontology](#concept-onto) 인덱스 | 원본과 편집을 합친 Object.<br />앱은 여기서 읽음 | 편집은 즉시 반영.<br />원본 변경은 [Funnel](#concept-funnel) 파이프라인이 실행될 때 반영 | Funnel |
| Funnel이 관리하는 Dataset | 원본의 변경분을 담은 changelog Dataset과 원본·편집을 합친 merged Dataset.<br />편집은 먼저 Funnel이 관리하는 큐에 쌓임.<br />사용자는 접근할 수 없음 | 원본에 새 트랜잭션이 생길 때 또는 편집이 있었다면 6시간마다 merged Dataset을 Build | Funnel(자동) |
| Materialized Dataset (선택) | 원본과 편집을 합친 각 Object의 최신 상태.<br />최신 스냅샷만 보장 | 편집 자동 전파(몇 분 지연) 또는 원본이 바뀔 때·6시간마다 | 사용자가 Ontology Manager에서 만듦 |

기본 설정에서는 편집한 property가 이후 원본이 바뀌어도 편집 값을 유지합니다(Apply user edits).\
예전 Object Storage v1에서는 편집하려면 writeback Dataset이 필요했습니다.\
OSv2에서 Materialization은 하류 파이프라인이나 대량 다운로드에 필요할 때만 만드는 선택 사항입니다.\
Materialized Dataset은 지난 트랜잭션이 계속 지워지므로 이력이 필요하면 하류 transform으로 따로 남깁니다.

공식 문서: [How user edits are applied](https://www.palantir.com/docs/foundry/object-edits/how-edits-applied) · [Materializations](https://www.palantir.com/docs/foundry/object-edits/materializations) · [Funnel batch pipelines](https://www.palantir.com/docs/foundry/object-indexing/funnel-batch-pipelines)

### 권한은 계층마다 따로 막아야 합니다

한 곳을 막았다고 해서 관련 데이터가 모두 보호되지는 않습니다.\
[Object security policy](#concept-osp)로 Object를 가려도 원본 [Dataset](#concept-dataset)과 [Media set](#concept-media)은 각각 따로 잠가야 합니다.\
Object security policy는 Ontology 밖에서 Dataset을 읽는 것을 막지 않으므로 Object가 아니라 Dataset을 분석하는 [Contour](#concept-analytics) 같은 도구는 Dataset 쪽 권한으로 따로 막아야 합니다.\
Object security policy 같은 행 단위 정책은 읽는 순간에만 적용되므로 [Function](#concept-function)이 읽어 만든 결과까지 보호하려면 Marking 같은 필수 통제를 함께 겁니다.\
[Action](#concept-action)은 쓰는 데이터의 보안을 Action의 로직이 정하므로 Marking이 붙은 데이터를 읽고 그보다 덜 제한된 곳에 쓸 수 있습니다.\
그래서 Marking이 붙은 데이터를 읽는 Action에는 read authorization(베타)을 설정합니다.\
OSDK 앱이 받는 토큰은 사용자(또는 서비스 유저) 권한과 Developer Console의 앱 제한이 모두 허용하는 리소스에만 접근하며 제한 없는(unrestricted) 앱은 사용자 권한이 허용하는 리소스에 모두 접근합니다([OSDK](#concept-osdk)).\
Application permissions를 쓰는 Developer Console 앱과 [Compute module](#concept-cm)은 로그인하거나 호출한 사용자가 아니라 서비스 유저 권한으로 동작합니다.\
[Media set](#concept-media)에 같은 경로로 올리면 경고 없이 덮어쓰므로 경로가 겹치지 않게 합니다.\
덮어쓰거나 삭제한 item도 기존 media reference나 직접 링크로 계속 접근할 수 있으므로 보존 정책으로 정리합니다.

공식 문서: [Managing object security](https://www.palantir.com/docs/foundry/object-permissioning/managing-object-security) · [Access control propagation](https://www.palantir.com/docs/foundry/security/access-control-propagation) · [Read and write authorizations](https://www.palantir.com/docs/foundry/action-types/read-write-authorizations) · [Application restrictions](https://www.palantir.com/docs/foundry/developer-console/application-restrictions) · [Developer Console 권한](https://www.palantir.com/docs/foundry/developer-console/permissions) · [Compute module 실행 모드](https://www.palantir.com/docs/foundry/compute-modules/execution-modes) · [Importing media](https://www.palantir.com/docs/foundry/media-sets-advanced-formats/importing-media) · [Media sets](https://www.palantir.com/docs/foundry/media-sets-advanced-formats/media-overview) · [Media set 설정](https://www.palantir.com/docs/foundry/media-sets-advanced-formats/media-set-settings)

이런 경우를 모은 표와 Restricted view·Object security policy 중 무엇을 쓸지는 [권한 노선](../foundry-access-route/) 글에 정리했습니다.

## 정리

- Foundry의 데이터는 주로 **원본 → Dataset → Ontology** 순서로 쌓입니다.\
  업무용 앱은 주로 Ontology를 직접 조회하고 쓰기는 Action을 거치며 복잡한 계산에는 Function 같은 로직을 씁니다.
- 사용자의 편집은 보통 **Action**을 거쳐 Ontology에 반영됩니다.\
  코드로 작성한 Function은 편집 내용을 계산할 뿐 Action 없이 직접 저장하지 않습니다.\
  Automate의 Logic effect가 staged writes를 끈 AIP Logic 함수의 편집을 Action 없이 적용하는 것은 예외입니다.
- Role과 행·열 단위 정책은 **계층마다 따로** 적용됩니다.\
  Object security policy, 원본 Dataset, Media set, OSDK 앱 제한을 각각 따로 설계하고 파생 데이터까지 보호하려면 Marking 같은 필수 통제를 함께 겁니다.
