처음으로 Palantir Foundry 프로젝트를 맡게 되었습니다.\

그래서 요구사항에 대한 기술 검토부터 일정 산정, 실제 구현까지 단계마다 어려움이 컸습니다.

Palantir Foundry는 데이터 수집과 가공, 업무 모델링, 애플리케이션 개발, 권한 관리를 하나의 플랫폼에서 다룹니다.\
범위가 넓은 만큼 처음 접하면 Dataset, Ontology, Funnel, Action, Function, OSDK처럼 낯선 이름이 한꺼번에 등장하고, 각각이 전체 구조의 어디에 놓이는지 파악하기 어렵습니다.

이 글은 Foundry의 주요 개념 23개를 **데이터가 흐르는 순서**로 배치한 개념 지도입니다.\
각 개념은 개발자에게 익숙한 React·MySQL·클라우드 서비스, 또는 일상과 업무의 장면에 빗대어 설명합니다.

## 전체 흐름

Foundry의 구성 요소는 크게 다섯 개의 층과 이를 감싸는 권한 체계로 나눌 수 있습니다.

1. **데이터**: Data Connection으로 외부 시스템의 데이터를 가져오고, Python transform이나 Pipeline Builder로 가공해 Dataset에 저장합니다.\
   가공 작업은 Build로 실행되고, Schedule에 따라 반복됩니다.\
   파일은 Media set에 따로 보관합니다.
2. **온톨로지**: Funnel이 Dataset의 데이터를 인덱싱해 Ontology의 Object로 만듭니다.\
   Ontology는 Dataset에 업무 의미(Object, Property, Link)를 부여한 계층이며, 업무용 앱은 이 계층을 읽고 씁니다.\
   Object type·Link type 같은 구조는 Ontology Manager에서 정의합니다.\
   여러 Object type이 공유하는 공통 형태는 Interface로 정의합니다.
3. **로직**: Action은 Ontology를 수정하고, Function은 조회와 계산을 담당합니다.\
   직접 만든 컨테이너 코드는 Compute module로, 조건에 따른 자동 실행은 Automate로, LLM 기반 로직은 AIP Logic으로 만듭니다.
4. **앱**: Workshop(노코드)이나 OSDK 기반 React 앱은 Ontology를 직접 조회하고, 쓰기와 계산은 로직 계층을 호출해 처리합니다.\
   Contour·Quiver·Object Explorer로는 코드 없이 데이터를 분석합니다.
5. **운영**: Ontology Manager, Global Branching, Marketplace는 특정 층에 속하지 않고 모든 층의 변경과 배포를 관리합니다.

이 전체를 Project·Role·Marking 권한 체계가 감쌉니다.\
여기에 더해 Object security policy는 Ontology 안에서 Object·Property 단위의 조회를, OAuth는 외부 앱의 인증을 담당합니다.

## 개념 지도

그림의 상자나 개념 목록의 이름을 누르면 해당 개념의 요약 카드가 표시됩니다.\
상자와 이름의 색은 개념이 속한 층을 나타냅니다.\
카드의 "비유로 보면"에서 개발자용과 일반용 비유 중 편한 쪽을 고를 수 있습니다.\
비유는 이해를 돕기 위한 근사치이며, 실제 동작의 세부 사항은 카드 하단의 공식 문서를 기준으로 봐야 합니다.

## 자주 혼동하는 지점

Foundry는 권한과 동작이 여러 계층에 나뉘어 있어서, 비슷해 보이는 설정이 실제로는 서로 다른 곳에서 결정되는 경우가 많습니다.\
아래는 그중 특히 혼동하기 쉬운 세 가지입니다.\
개념 이름을 누르면 개념 카드가 해당 개념으로 바뀝니다.

### 조회 · 제출 · 저장은 서로 다른 곳에서 결정됩니다

"사용자가 이 Object를 수정할 수 있는가"라는 질문은 실제로는 세 개의 독립된 질문으로 나뉩니다.

| 질문 | 결정하는 곳 | DB 비유 | 일상 비유 |
| --- | --- | --- | --- |
| 누가 어떤 Object를 볼 수 있는가? | [Object security policy](#concept-osp) | 모든 SELECT에 자동으로 붙는 WHERE | 같은 명부를 열어도 내 담당 줄만 보임 |
| 이 Action을 제출할 수 있는가? | [Submission criteria](#concept-action) | UPDATE 전에 실행되는 IF 검사 | 결재 조건을 통과해야 신청서를 낼 수 있음 |
| 변경은 언제 실제로 저장되는가? | [Action](#concept-action)이 실행될 때만 | COMMIT.<br />[Edit function](#concept-function)은 변경할 SQL을 만드는 데까지만 관여 | 신청서가 처리되어야 반영됨.<br />계산기로 미리 계산해 둔 것만으로는 반영되지 않음 |

### OSDK 토큰의 권한은 세 범위의 교집합입니다

OSDK로 만든 앱이 받는 토큰은 사용자 권한, Developer Console에 설정한 앱 제한(application restrictions), 앱이 요청한 scope 세 가지가 모두 허용하는 범위만 접근할 수 있습니다.

| 범위 | 주문 | 고객 | 재고 |
| --- | :-: | :-: | :-: |
| 사용자 권한 | ✓ | ✓ | ✓ |
| 앱 제한 | ✓ | ✗ | ✓ |
| 요청 scope | ✓ | ✓ | ✗ |
| **토큰 접근 범위** | **✓** | ✗ | ✗ |

앱 제한은 앱이 받을 수 있는 권한의 보장된 상한입니다.\
요청 scope는 앱 코드가 토큰을 요청할 때 정하는 값으로, 그 상한 안에서 범위를 더 좁히는 역할만 합니다([OSDK](#concept-osdk)).

### 권한이 서로 연동되지 않는 곳

한 곳을 막았다고 해서 관련 데이터가 모두 보호되지는 않습니다.\
아래 경우는 각각 따로 막아야 합니다.

<div class="nowrap-last-col">

| 막은 곳 | 그래도 열려 있는 곳 | 따로 해야 할 일 |
| --- | --- | --- |
| [Object security policy](#concept-osp)로 Object를 가림 | 원본 [Dataset](#concept-dataset) | Dataset 권한을 따로 설정 |
| [Object security policy](#concept-osp)로 media reference property를 가림 | [Media set](#concept-media)에서 파일을 직접 가져오기 | Media set 권한을 따로 설정 |
| [Media set](#concept-media)의 파일을 같은 경로에 덮어써 교체 | 이전 파일 (기존 media reference로 접근 가능) | 덮어쓴 item의 보존 정책 설정 |
| 사용자별 권한으로 데이터를 제한 | Application permissions를 쓰는 [Compute module](#concept-cm) (호출한 사용자가 아니라 서비스 유저 권한으로 동작) | 서비스 유저에게 필요한 권한만 부여 |

</div>

## 정리

- Foundry의 데이터는 **원본 → Dataset → Ontology** 순서로 쌓입니다.\
  업무용 앱은 Dataset이 아니라 Ontology를 직접 조회하고, 쓰기와 계산은 로직을 거칩니다.
- 사용자의 편집은 **Action**을 거쳐 Ontology에 반영됩니다.\
  Function은 편집 내용을 계산할 뿐, Action 없이 직접 저장하지 않습니다.
- 권한은 **계층마다 독립적**입니다.\
  Object security policy, 원본 Dataset, Media set, OSDK 앱 제한을 각각 따로 설계해야 합니다.
