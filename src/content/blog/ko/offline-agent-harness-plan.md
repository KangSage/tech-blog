> 하네스(harness, AI 코딩 도구를 감싸는 규칙·스크립트·설정 묶음)를 처음부터 설계했다.
> 환경은 제약이 많았다. 이 글은 결과물보다 "계획을 어떻게 세웠나" 에 집중한다.
> 특정 회사, 플랫폼 이야기는 뺐다. 비슷한 제약에서 쓸 수 있는 일반 원칙만 남겼다.

---

## 1. 출발점: 제약이 설계를 정한다

처음에 가진 것은 이것뿐이었다.

- **완전 오프라인 컨테이너.** 인터넷 없음. `npm install`, `pip install` 안 됨.
- **매번 사라지는 홈 폴더.** 컨테이너를 다시 띄우면 git repo 만 남는다. 도구 설정, 세션 기록, 로그는 모두 사라진다.
- **오픈소스 coding agent (코딩 에이전트) 2개.** opencode 와 codex CLI.
- **모델 2개.** 똑똑하지만 rate limit (요청 한도) 에 자주 걸리는 큰 모델(429 에러). 빠르지만 작은 모델.
- **복사·붙여넣기 불가.** 밖에서 만든 파일을 안으로 가져갈 수 없다. 프롬프트는 손으로 쳐야 한다.
- **작은 팀.** agentic coding (AI 에게 작업을 맡기는 개발) 경험자는 1명. 나머지는 처음.
- **엉망인 요구사항.** 지저분한 기능정의 스프레드시트 + 계속 바뀌는 바이브 코딩 HTML 샘플. 둘이 서로 다르다.

여기서 첫 교훈이 나온다.

**제약을 먼저 다 적는다. 해법은 그 다음이다.**
"git repo 만 남는다" 한 줄이 이후 모든 설계를 정했다. 기억, 기록, 인수인계가 전부 "git 안의 파일" 이 됐다.

## 2. 첫 단계는 만들기가 아니라 점검 순서였다

처음 받은 질문은 "repo 에 하네스를 넣었는데 왜 안 먹히나" 였다.
그래서 계획의 첫 문서는 설계가 아니라 **진단 체크리스트** 였다.

### 제일 흔한 원인은 "조용한 무시"

에러가 나면 차라리 쉽다. 진짜 문제는 설정이 **에러 없이 무시** 되는 경우다.

- **trust (신뢰) 정보가 사라짐.** codex 는 신뢰된 프로젝트에서만 repo 의 설정과 hook 을 읽는다. 그 신뢰 기록은 홈 폴더에 있다. 컨테이너가 새로 뜨면 기록이 없다. repo 설정이 조용히 무시된다.
- **실행 위치가 repo 밖.** 두 도구 모두 현재 폴더에서 위로 올라가며 설정을 찾는다.
- **폴더 이름 오타.** `skill/` 과 `skills/` 는 다르다. 단수·복수 하나로 로드가 안 된다.
- **frontmatter (파일 머리 메타데이터) 오류.** skill 의 `name` 이 폴더 이름과 다르면 로드 안 된다.

### canary (확인용 표식) 로 한 층씩 증명한다

모든 층을 한 번에 켜지 않았다. 층마다 눈에 띄는 표식을 넣고, 하나씩 확인했다.

```
AGENTS.md 맨 위:  "ping" 이라고 하면 "AGENTS-OK" 만 답한다.
skill:           "canary skill" 이라고 하면 "SKILL-OK" 만 답한다.
hook:            실행되면 .harness/hook.log 에 날짜 한 줄.
memory:          facts 에 "비밀 단어 BANANA-42" → 새 세션에서 물어본다.
```

`AGENTS-OK` 가 안 나오면 그 뒤 층은 보지 않는다. 앞 단계가 실패하면 뒤는 의미가 없다.

**교훈: hook 은 먼저 "파일에 한 줄 쓰기" 로 증명한다. 진짜 로직은 그 다음이다.**

### 사라지는 홈 폴더는 매번 다시 만든다

홈 설정이 사라지면, 컨테이너 시작 때 다시 만들면 된다. `source` 하는 스크립트 1개를 두었다.

- 도구의 홈 폴더 위치를 환경 변수로 repo 안 (gitignore 된 곳) 으로 옮긴다.
- trust 기록을 **현재 절대 경로로** 매번 새로 쓴다.
- 단, 원래 홈 설정에 플랫폼이 넣어 준 MCP 서버나 인증이 있을 수 있다. 그래서 원래 파일을 **먼저 복사하고**, 그 위에 repo 설정을 합친다.

마지막 항목은 처음 설계에 없었다. 다음 문서를 쓰다가 "내가 앞에서 준 방법이 이걸 지운다" 를 발견했다.
**새 문서를 쓸 때는 앞 문서와 충돌하는지 먼저 본다.** 이 습관이 계획 전체에서 여러 번 사고를 막았다.

## 3. "부탁" 을 "강제" 로 바꾼다

두 번째 문제는 "AI 가 작업 기록을 안 남긴다" 였다. AGENTS.md 에 분명히 써 두었는데도.

원인은 단순하다.

1. **AGENTS.md 의 지시는 부탁이다.** 모델은 일이 끝나면 바로 멈춘다. 마지막 정리 단계가 잘 빠진다. 작은 모델일수록 더 빠진다.
2. **긴 세션은 compaction (대화 압축) 된다.** 맨 앞 지시가 약해진다.
3. **저장 위치가 repo 밖이면** 남겨도 사라진다.

그래서 기록을 두 층으로 나눴다.

| 층 | 누가 | 특징 |
|---|---|---|
| 기계 기록 | hook (모델과 무관) | 항상 남는다. 시간, `git status`, 마지막 AI 답 일부 |
| 모델 요약 | AI (강제) | 파일을 바꿨는데 기록이 없으면, Stop hook 이 멈춤을 막고 "기록 써라" 를 다음 지시로 넣는다 |

```python
# Stop hook 의 핵심 (개념)
if 바뀐_파일 and 기록_파일이_더_오래됨 and not data.get("stop_hook_active"):
    print(json.dumps({"decision": "block",
                      "reason": "작업 기록을 쓰고, 새 사실은 메모리에 저장하고 끝내라."}))
```

`stop_hook_active` 확인이 중요하다. 이것이 없으면 무한 반복에 빠진다. 강제는 **한 번만** 한다.
기록과 메모리 저장도 **한 번의 block 에 같이** 넣었다. 두 번 막으면 루프 위험이 커진다.

**교훈: 중요한 규칙은 문서에 쓰지 말고 기계에 건다. 문서는 무시될 수 있다. 명령은 무시되지 않는다.**

이 원칙은 나중에 계속 다시 나온다.

## 4. 기억, 기록, 진행 중인 일을 나눈다

세션이 사라지는 환경에서는 "무엇을 어디에 남기나" 가 핵심이다. 세 가지로 나눴다.

| 폴더 | 비유 | 자동 로드 |
|---|---|---|
| `docs/history/` | 일기. 한 일 기록. 계속 쌓임 | 안 함 |
| `.memory/` | 정리된 지식. 결정, 함정, 사실 | **색인만** 함 |
| `.work/` | 지금 진행 중인 일 | 현재 일감만 함 |

원칙 3개:

1. **저장 = git 파일.** 벡터 DB, 외부 메모리 서버는 설치도 유지도 안 된다. 마크다운 + git 은 두 도구 모두 그냥 읽는다. diff 로 리뷰도 된다.
2. **읽기 = 강제.** "읽어라" 부탁 대신 설정(`instructions`)과 SessionStart hook 으로 매 세션 자동 주입.
3. **쓰기 = 반강제.** 끝날 때 Stop hook 또는 명령으로 저장시킨다.

메모리는 **색인 파일(한 줄씩) + 상세 파일** 로 나눴다. 색인만 항상 읽고, 상세는 필요할 때 연다. context (문맥 창) 를 아끼기 위해서다.
그리고 메모리 저장 규칙에 이것을 넣었다: "코드나 git 로그로 알 수 있는 것은 저장하지 않는다." 안 그러면 메모리가 쓰레기통이 된다.

## 5. 세션 대신 인수인계 쪽지

"어제 하던 일 이어하기" 가 안 되는 이유는 세 가지였다.

1. 세션 기록이 홈 폴더에 있다 → 사라진다.
2. commit 안 한 작업은 사라지거나, 남아도 "어디까지 했는지" 모른다.
3. "다음에 할 일" 이 머릿속에만 있다.

그래서 **세션을 살리려 하지 않았다. 내일의 나(또는 AI)에게 쪽지를 남겼다.**

일감 1개 = 파일 1개. 목표, 완료 조건, 단계 체크박스, 막힌 것, 건드린 파일. 그리고 가장 중요한 칸:

```markdown
## 다음 행동 (딱 1개, 바로 실행 가능하게)
tests/test_x.py 에 빈 값 케이스 추가 후 `pytest tests/test_x.py -k empty` 실행.
```

"테스트 마무리" 는 안 된다. 생각 없이 바로 시작할 수 있는 한 줄이어야 한다.

- 퇴근 전 `handoff`: 일감 갱신, 기록, 메모리 저장, WIP commit. 깨진 상태도 commit 하고 "깨진 상태" 라고 적는다.
- 아침 `이어서`: 일감 + 자동 저장 + `git log` 를 읽고, **파일 내용과 실제 상태가 다르면 그 차이부터** 보고한다. 3줄 요약 후 OK 받고 시작.
- 안전망: handoff 를 깜빡해도 hook 이 매 턴 마지막 상태를 덮어쓴다.

나중에 규칙 하나를 더 넣었다. **self-contained (자기 완결형).** 일감, 요청서, 인수인계 파일은 그 파일만 보고 처음 보는 사람이나 AI 가 실행할 수 있어야 한다. "아까 말한", "위에서" 금지. 확인은 작은 모델에게 파일만 주고 "빠진 정보 목록" 을 받는 방식으로 했다.

## 6. AI 가 막히면 사람에게 요청서를 쓴다

AI 가 코드로 못 하는 일이 있다. UI 에서 권한 주기, 승인 받기, 외부 확인.
이때 AI 는 보통 두 가지 중 하나를 한다. 그럴듯하게 우회하거나, 멈춰서 기다린다. 둘 다 나쁘다.

이 개념에는 이름이 있다. **human-in-the-loop (사람 참여형).** 일부 에이전트 프레임워크는 실행을 멈추고(interrupt), 사람이 답하면 그 지점부터 다시 실행(resume)한다.
우리 환경은 세션이 사라진다. 그래서 **멈춘 지점을 메모리가 아니라 파일에 저장** 했다.

요청서의 필수 칸:

- 왜 필요한가
- 해 줄 일 (처음 보는 사람도 따라할 수 있게. 값은 그대로 복사 가능하게)
- **완료 확인 방법 (AI 가 직접 실행할 명령)**
- 결과 (사람이 적음)

핵심은 "완료 확인" 이다. 사람 말만 믿지 않는다. 다음 날 `이어서` 하면 AI 가 확인 명령부터 돌린다. 통과하면 일감의 막힘을 풀고, 실패하면 무엇이 아직인지 한 줄로 말한다.

그리고 **AI 는 기다리며 놀지 않는다.** 막히지 않은 다른 단계가 있으면 그것을 한다. 없으면 깔끔히 인수인계하고 멈춘다.
세션 안에서 `while` 루프로 기다리는 방법은 버렸다. 컨테이너가 죽으면 기다림도 사라지고, 대기 중 재시도로 비용만 쓴다.

## 7. 요구사항 분석: AI 실력이 아니라 일의 모양 문제

며칠 동안 AI 로 요구사항을 분석했는데 결과가 엉망이었다. 원인을 정리하니 AI 실력 문제가 아니었다.

1. **정답이 없는 입력.** 스프레드시트와 HTML 이 다르다. AI 는 어느 쪽이 맞는지 모른다. 그래서 섞거나 지어낸다.
2. **너무 큰 한 덩어리.** "전체 분석 → 설계" 는 context 를 넘는다. 압축이 앞 내용을 버린다.
3. **스프레드시트를 AI 가 직접 읽음.** 병합 셀, 여러 줄 셀, 숨긴 시트, 색으로 표시한 의미. 구조가 깨진다.
4. **HTML 을 통째로 읽음.** 대부분이 의미 없는 토큰이다.
5. **중간 결과가 파일로 안 남음.** 다음 날 처음부터.
6. **"끝" 의 기준이 없음.** AI 는 긴 문서를 만들고 멈춘다. 검증할 방법이 없다.
7. **질문할 사람이 빠짐.** 분석의 핵심은 "현업에게 물을 질문 찾기" 다. 묻지 않은 분석은 추측이다.

한 줄로: **모순된 입력 + 거대한 한 번 작업 + 저장 없음 = 엉망.**

바꾼 원칙 4개:

1. **기계적 변환은 script 가 한다. 판단만 AI 가 한다.** 스프레드시트 → 시트별 md 표 (병합 셀 채움, 행 번호 붙임). HTML → 화면·입력·버튼 목록. 수천 줄이 수백 줄이 된다.
2. **진실은 하나만 둔다: 기능 장부 (ledger).** 스프레드시트도 HTML 도 "입력" 일 뿐이다. 장부의 행마다 출처(`시트!행번호`, 화면 id)를 단다.
3. **작게 자른다.** 한 세션 = 화면 1개.
4. **모순은 고치지 말고 질문으로 만든다.** 질문에는 선택지 (a)(b)(c) 를 준다. 현업이 빨리 답한다. `확정` 은 현업 답을 받은 것만. AI 가 확정하지 않는다.

HTML 이 또 바뀌면 전체를 다시 분석하지 않는다. 변환 script 를 다시 돌리고 **git diff 만** AI 에게 준다. 이미 확정된 행이 바뀌면 자동 수정하지 않고 질문으로 만든다.

### 기대치 맞추기

팀장은 "AI 가 다 해준다" 고 기대했다. 이런 비유를 썼다.

> AI 는 아주 빠른 신입이다. 매일 아침 기억을 잃는다. 업무를 모른다. 받은 자료를 그대로 믿는다.

| 잘 됨 | 잘 안 됨 |
|---|---|
| 입력이 깨끗하고 작음 | 입력이 크고 서로 모순 |
| 완료 기준이 명확 (테스트 통과) | "분석 잘 해줘" |
| 기존 패턴 반복 | 처음 보는 업무 판단 |
| 결과를 바로 확인 가능 | 며칠 뒤에야 맞는지 앎 |

말보다 데모가 낫다. 같은 화면을 두 방식으로 돌린다. A 는 "통째로 분석해서 설계해". B 는 script → 장부 → 질문. B 에는 출처가 있고 질문 목록이 나온다. 그 질문 목록을 보여주며 말한다. "이건 AI 도 우리도 모릅니다. 현업만 압니다."
그리고 시니어에게 가장 잘 맞는 역할을 제안했다. 현업 창구, 질문 답 받아오기, 우선순위 결정. AI 가 못 하는 일이다.

## 8. 설계를 "손으로 칠 프롬프트" 로 바꾼다

여기까지 설계 문서가 여러 개 쌓였다. 그런데 큰 벽이 있었다. **파일을 안으로 가져갈 수 없다.** 복사도 안 된다.

### 1차: 단계별 긴 프롬프트

처음에는 설계를 순서대로 프롬프트로 바꿨다. 단계마다 프롬프트 1개, 확인(✅) 1개, commit.
하지만 손으로 치기에는 너무 길었다.

### 2차: 계획 파일 한 번 + 한 줄 명령

전략을 바꿨다.

1. **계획 파일을 딱 한 번 친다.** `.harness/PLAN.md`, 약 40줄. 짧은 키워드 위주. 상세 구현은 AI 가 채운다.
2. git 에 남으니 다시 칠 일이 없다. 팀원도 그대로 쓴다.
3. 그 다음부터는 한 줄만 친다.

```
PLAN 3 해
```

계획 파일 첫 줄에 공통 규칙을 넣었다.

```
각 단계: 만들고 → 결과 보고. 외부 패키지 금지. 표준 라이브러리만.
확인 명령은 실행하지 말고 보여만 줘. 확인은 내가 함. 요청한 단계만. 다음 단계 미리 하지 마.
```

"확인은 내가 함" 은 실제로 겪고 넣었다. AI 가 확인한다며 에이전트를 또 하나 띄우면 느리고, 한도에도 걸린다.

### 손으로 친 파일은 검수부터

손으로 치면 오타가 생긴다. 그래서 첫 단계 전에 AI 에게 **검수만** 시켰다. "고치지 마. 표로: 줄 | 문제 | 제안 | 확실 or 추정."
문제가 많으면 하나씩 고치지 않는다. 기준(표준 라이브러리만, repo 루트 기준 등)을 주고 한 번에 고치게 한다.

경로 문제가 많이 나왔을 때는, 경로를 하나씩 고치는 대신 **규칙 한 줄** 을 계획 파일에 넣었다.

```
모든 경로는 repo 루트 기준. 스크립트는 시작할 때 루트로 cd.
파일 쓰기 전에 부모 폴더 생성. 읽을 파일이 없으면 에러 대신 빈 기본값.
```

이 한 줄이 경로 문제를 한꺼번에 없앴다.

**교훈: 같은 종류의 문제가 여러 개면, 문제를 고치지 말고 규칙을 하나 추가한다.**

### 아침 런북

설계 문서, 프롬프트 문서가 흩어져 있으면 출근해서 무엇부터 할지 모른다. 그래서 마지막에 **런북 (runbook, 순서대로 따라하는 절차서)** 하나로 세웠다.
표시를 4개만 썼다. 🖥️ 터미널에 친다 / 🤖 AI 에게 친다 / ✋ 사람이 한다 / ✅ 확인. 통과해야 다음으로 간다.

## 9. 실제로 부딪히고 고친 것

계획은 현장에서 계속 바뀌었다. 기억에 남는 것들.

- **플러그인 폴더가 오프라인에서 멈춤.** repo 에 opencode 설정 폴더(`.opencode/`)가 있으면, opencode 가 시작할 때 플러그인 패키지를 설치하려 한다. 오프라인이라 그대로 멈췄다. 폴더를 없애니 약 9초에 떴다. 해결: 설정 파일을 다른 위치에 두고 환경 변수로 지정. 플러그인은 시작 스크립트가 홈 폴더에 링크.
  → **오프라인 환경에서는 "도구가 몰래 네트워크를 쓰는 지점" 부터 의심한다.**
- **모델 이름은 정확히.** 화면에 보이는 짧은 이름과 설정에 쓰는 실제 id 가 달랐다. 도구마다 요구하는 형식도 달랐다. 추측하지 않고 도구의 모델 목록 명령 출력을 그대로 쓰게 했다.
- **터미널 멀티플렉서 없음.** 창이 꺼지면 에이전트가 뒤에서 살아 있다. "이미 열려 있음" 에러가 났다. 아침 첫 단계에 "숨은 프로세스 찾아서 끄기" 를 넣었다.
- **429.** 도구가 다른 모델로 자동 전환하지 않는다. 재시도 횟수를 늘리고, 실패하면 작은 모델로 다시 도는 wrapper (감싸는 스크립트) 를 두었다. 기본 모델을 아예 작은 모델로 바꾸고, 판단 작업만 큰 모델로 올렸다. 팀이 동시에 큰 모델을 쓰면 한도에 더 자주 걸리기 때문이다.
- **1인용 → 팀용.** 처음 계획은 혼자 쓰는 구조였다. 여러 명이 같은 repo 를 쓰면 같은 일감 파일, 같은 기록 파일, 같은 번호에서 충돌한다. 해결: 사람마다 파일을 나누고(`.work/<나>/`), 기록 파일과 일감 ID 에 이름을 붙였다. "나" 는 git 브랜치 이름의 앞부분(`<아이디>/...`)에서 읽었다. 요구사항 장부도 화면별 파일로 나눴다.
  → **새 파일을 설계할 때는 처음부터 "사람별 또는 화면별" 인지 묻는다.**
- **MCP 중복 조회.** AI 가 같은 MCP 조회를 계속 반복했다. 조회 결과를 캐시 파일에 요약하고, 같은 조회 전에 캐시부터 읽게 했다. 다시 조회는 대상을 바꿨거나 1시간이 지났을 때만.
- **토큰 절약.** AGENTS.md 60줄 이하, 긴 설명은 skill 로. 메모리 색인 30줄 이하. 세션 시작 주입 합계 2000자 이하. 파일 통째 읽기 금지(검색 후 필요한 줄만). 코드를 다시 출력하지 말고 diff 만.
- **AI 말투.** 결론 먼저, 짧은 문장, 보고는 3줄(한 일 / 확인 결과 / 다음 행동), 확인 안 한 것은 "추정". 단, 일감·요청서·skill 파일은 예외다. 그것들은 자세해야 한다. 짧게 말하기와 self-contained 가 부딪히면 self-contained 가 이긴다.

## 10. 나중에 붙인 두 가지: slop 과 머지 사고

### AI slop (AI 가 만드는 쓰레기 코드) 줄이기

외부에서 본 좋은 방법들을 우리 환경에 맞춰 골랐다.

- **코딩 규칙 skill.** 모르면 가정하지 말고 질문. 요청한 줄만 고침. 새 추상화, 새 파일 금지. 표준 라이브러리에 있으면 직접 짜지 않음. 시작 전에 성공 기준(확인 명령)부터.
- **완료 전 증거 skill.** "완료" 라고 말하기 전에 확인 명령을 새로 실행하고 결과를 붙인다. "될 거예요, 아마" 금지.
- **linter 대신 검색 스크립트.** 오프라인이라 linter 를 설치할 수 없다. 이미 있는 linter 만 쓰고, 없으면 `rg` 로 `console.log`, 주석 처리된 코드, `TODO`, 빈 `catch` 를 찾아 exit 1.

여기서도 3장의 교훈이 그대로다. **md 규칙은 AI 가 무시할 수 있다. 명령(lint, test)은 무시하지 못한다.** 그래서 세 번째가 가장 중요하다. AI 코드에서 싫은 패턴을 볼 때마다 스크립트에 규칙을 하나씩 늘린다.

### AI 가 머지 충돌을 풀다 코드를 지어낸 사고

오래 떨어져 있던 브랜치를 AI 에게 "머지해" 통째로 맡겼다. AI 는 양쪽 의도를 모른다. 그래서 그럴듯한 새 코드를 만들어 "합쳤다". 검사할 방법이 없어서 그대로 들어갔다.

대책은 세 겹이다.

1. **충돌을 작게.** 매일 아침 기본 브랜치를 받는다. 브랜치는 짧게.
2. **AI 규칙.** 백업 브랜치 먼저. 충돌 파일 1개씩. 양쪽 `git log` 로 의도를 준다. 결과의 모든 줄은 어느 한쪽에 있던 줄이어야 한다. 새 코드가 필요하면 멈추고 묻는다. lock 파일은 사람이 정한다.
3. **기계적 검사.** 머지 commit 의 combined diff 에서 `++` 로 시작하는 줄은 두 부모 어디에도 없던 줄이다.

```bash
git show --cc HEAD | grep '^++[^+]'
# 출력 0줄 = 지어낸 줄 없음
```

일부러 지어낸 줄 하나를 넣은 테스트 머지에서, 이 명령이 그 줄만 정확히 잡았다.
git 설정 두 개도 도움이 된다. `merge.conflictstyle zdiff3` (충돌에 원래 코드도 같이 보여줌), `rerere.enabled true` (한 번 푼 충돌을 기억).

## 11. 정리: 계획을 세우며 남은 원칙

1. **제약부터 다 적는다.** "무엇이 남고 무엇이 사라지나" 가 설계를 정한다.
2. **진단 순서를 먼저 만든다.** 조용히 무시되는 설정이 제일 흔하다. canary 로 한 층씩 증명한다.
3. **부탁 말고 강제.** 중요한 규칙은 hook, 스크립트, 확인 명령에 건다.
4. **세션을 살리려 하지 말고 쪽지를 남긴다.** "다음 행동" 은 바로 실행 가능한 한 줄.
5. **기계 일은 script, 판단만 AI.** 입력이 작고 깨끗할수록 작은 모델로도 된다.
6. **모순은 고치지 말고 질문으로.** 확정은 사람이 한다.
7. **사람 말만 믿지 않는다.** 요청서에는 AI 가 실행할 완료 확인 명령을 넣는다.
8. **같은 문제가 여러 개면 규칙 하나를 추가한다.**
9. **새 문서를 쓸 때 앞 문서와 충돌하는지 본다.**
10. **처음부터 팀용으로.** 공유 파일은 사람별 또는 단위별로 나눈다.
11. **확인 안 한 것은 "추정" 이라고 적는다.** 계획 문서마다 끝에 추정 목록을 두었다. 현장에서 smoke test (최소 동작 확인) 로 하나씩 지웠다.

마지막으로 하나. 이 계획은 한 번에 나오지 않았다. "왜 안 되지?" 질문 하나에 문서 하나가 생겼고, 현장에서 막힐 때마다 몇 줄씩 고쳤다.
**처음부터 완벽한 하네스를 설계하려 하지 말고, 진단 → 작은 단계 → 확인 → commit 을 반복한다.** 하네스도 결국 그렇게 만들어진다.
