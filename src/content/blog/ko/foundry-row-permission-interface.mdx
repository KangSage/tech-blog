## TL;DR

- **한 일**: 행 권한 속성 `viewerGroupIds`를 가진 6개 오브젝트 타입을 Interface `KsSecured` 하나로 묶었습니다.
- **얻은 것**: 권한 값이 빠진 객체를 찾는 점검이 Interface 조회 한 번으로 줄었고 권한 값을 쓰는 코드는 객체의 실제 타입을 몰라도 됩니다.\
  새 권한 타입은 Interface만 구현하면 점검 대상이 됩니다(브랜치에서는 인덱싱이 끝난 뒤).\
  다만 누가 볼 수 있는지 계산하는 규칙은 타입마다 따로 추가해야 합니다.
- **함정 1**: 이 환경에서는 브랜치에서 새로 만든 Interface로 편집하는 함수가 CI와 브랜치 미리보기 실행에서 실패했습니다.\
  Interface 정의를 먼저 Main에 병합하고 쓰기 코드는 다음 브랜치에서 병합해 해결했습니다.
- **함정 2**: 이 환경에서는 구현 타입마다 *Enable interface actions*가 꺼져 있어서 Action 실행 단계에서야 실패했습니다.\
  6개 타입 모두에서 이 설정을 켜고 브랜치 인덱싱이 끝나기를 기다린 뒤 통과했습니다.
- **치른 비용**: 병합이 두 번으로 늘었고 타입마다 설정을 켜고 인덱싱을 기다려야 했습니다(이 환경에서는 Action 저장 뒤 타입 하나의 인덱싱에 약 10분 걸린 적이 있습니다).\
  이 설정을 켜야 Interface 편집이 적용됐으므로 권한 값을 쓰는 Action의 제출 조건(Submission criteria)도 함께 점검하는 것이 좋습니다.
- **언제 쓸까**: 권한 타입이 많을수록 얻는 것이 크다고 봅니다.\
  권한 타입이 한두 개뿐이라면 두 번의 병합과 설정 관리 비용이 더 클 수 있으니 TypeScript 제네릭 함수로 중복만 줄이는 편이 나을 수 있습니다.

## 배경: 행 권한이 걸린 6개 오브젝트 타입

Foundry에서 행 단위 권한(Row-level Security)을 걸다 보면 권한 값을 가진 오브젝트 타입이 금방 여러 개로 늘어납니다.\
제 검증 환경에서도 6개 타입이 같은 이름의 권한 속성 `viewerGroupIds`를 각자 가지고 있었습니다.\
그래서 이 값을 점검하거나 고치는 코드도 타입마다 따로 써야 했습니다.

먼저 이 글에 자주 나오는 Foundry 용어를 짧게 정리합니다.

- **오브젝트 타입(Object type)**: Ontology에서 업무 대상 하나를 나타내는 타입입니다.\
  데이터베이스 테이블 하나에 대응하는 모델 클래스로 생각하면 쉽습니다.
- **Object Security Policy**: 오브젝트 타입에 거는 행 단위 접근 규칙입니다.\
  사용자 속성(소속 그룹 ID 등)과 객체 속성을 비교하는 [Granular Policy](https://www.palantir.com/docs/foundry/platform-security-management/manage-granular-policies)로 행마다 보여 줄지 정합니다([공식 문서](https://www.palantir.com/docs/foundry/object-permissioning/object-security-policies)).
- **Action**: Ontology의 객체를 바꾸는 정해진 작업 단위입니다.\
  이 글의 Action은 모두 TypeScript 함수가 바꿀 내용(Edits)을 계산해 돌려주면 Action이 그 내용을 Ontology에 반영하는 <strong>함수 기반 Action(Function-backed Action)</strong>입니다.
- **Edit-only 속성**: 백킹 데이터셋(Backing dataset)의 컬럼과 연결하지 않고 Ontology 편집(Action 등)으로만 값을 넣는 속성입니다.\
  Object Storage V2 타입에서만 쓸 수 있고 속성 자체의 권한은 백킹 데이터셋 중 하나를 따릅니다([공식 문서](https://www.palantir.com/docs/foundry/object-link-types/edit-only-properties)).
- **Global Branching**: Ontology 설정과 코드 레포를 한 브랜치에서 함께 고치고 Proposal로 기본 브랜치에 병합하는 기능입니다([공식 문서](https://www.palantir.com/docs/foundry/global-branching/core-concepts)).\
  코드 레포의 기본 브랜치는 `master`, Ontology의 기본 브랜치는 `Main`이라고 부릅니다.
- **브랜치 인덱싱(Branch indexing)**: 브랜치에서 정의를 바꿨거나 Action으로 수정할 오브젝트 타입을 그 브랜치에서 조회·편집할 수 있게 색인하는 작업입니다.\
  이 환경에서는 인덱싱이 끝나기 전까지 그 타입을 수정하는 Action을 브랜치에서 실행할 수 없었습니다.
- **OSDK와 `rune`**: [OSDK(Ontology SDK)](https://www.palantir.com/docs/foundry/ontology-sdk/typescript-osdk)는 Ontology 정의로 생성한 타입으로 객체를 다루는 TypeScript SDK입니다.\
  `rune`은 이 환경의 TypeScript Functions 레포 템플릿에 들어 있는 CLI이며 로컬에서 함수를 탐색(Discovery)하고 실행해 볼 때 썼습니다.
- **함수 탐색(Discovery)**: 함수 레포를 빌드할 때 어떤 함수가 있고 각 함수가 어떤 오브젝트 타입을 읽고 수정하는지 분석해 메타데이터로 등록하는 단계입니다.
- **백필(Backfill)**: 비어 있거나 어긋난 권한 값을 규칙에 맞게 다시 계산해 한꺼번에 채우는 작업입니다.

검증 환경에서 행 단위 권한을 거는 타입은 아래 6개이고 모두 그룹 ID 목록 속성 `viewerGroupIds`(배열)를 가집니다.

| 타입 | 설명 |
|---|---|
| `KsProject` | 프로젝트 |
| `KsDocument` | 프로젝트 산하의 문서 |
| `KsRevision` | 문서의 작업본·리비전 |
| `KsRevisionSnapshot` | 리비전에 속한 참조 사본 |
| `KsLineItem` | 세부 항목 |
| `KsGrant` | 권한 부여 기록 |

각 타입의 Object Security Policy는 **사용자가 속한 그룹이 객체의 `viewerGroupIds`와 하나라도 겹치거나 사용자가 관리자 그룹(`ks-app-admin`)에 속할 때만** 그 행을 보여 줍니다.

`viewerGroupIds`는 **Edit-only 속성**으로 만들었습니다.\
파이프라인(Transform)이 데이터셋을 다시 빌드해도 이미 부여한 권한 값이 덮어써지지 않게 하려는 것입니다.

대신 신경 쓸 점이 하나 생깁니다.\
Transform이 새 행을 만들면 그 행의 `viewerGroupIds`는 처음에 비어 있고(`null`) 일반 사용자에게 보이지 않습니다.\
그래서 객체가 생긴 뒤 Action으로 권한 값을 채워야 합니다(Automate로 자동화할 수도 있습니다).\
실무에서도 원천 데이터가 파이프라인으로 들어오는 구조라면 똑같이 겪는 상황입니다.

결국 이 구조에서는 두 가지 작업이 계속 반복됩니다.

1. **점검(Audit)**: 6개 타입을 모두 훑어 `viewerGroupIds`가 비어 있는 객체가 있는지 확인합니다.
2. **쓰기(Mutation)**: 권한 부여·회수·백필 Action이 실행될 때 영향을 받는 객체의 `viewerGroupIds`를 고칩니다.

Interface를 쓰기 전에는 두 작업 모두 6개 타입을 하나씩 조회하고 타입별 편집 코드를 길게 늘어놓아야 했습니다.

## 설계: `KsSecured` Interface

[Ontology Interface](https://www.palantir.com/docs/foundry/interfaces/interface-overview)는 여러 오브젝트 타입이 공통으로 가지는 모양(속성 구조)을 선언하는 추상 타입입니다.\
Interface만으로는 객체를 만들 수 없고 모든 객체는 Interface를 구현한 실제 오브젝트 타입에 속합니다.\
TypeScript의 `interface`와 비슷하다고 보면 됩니다.

`KsSecured`는 이렇게 설계했습니다.

- **`KsSecured`에는 `viewerGroupIds` 속성 하나만 둡니다.**\
  화면에 보이는 이름은 *Viewer Group Ids*입니다.
- **6개 오브젝트 타입이 모두 `KsSecured`를 구현합니다.**\
  오브젝트 타입마다 *Interfaces* 탭에서 Interface를 추가하고 Interface 속성을 그 타입에 이미 있던 `viewerGroupIds` 속성에 연결합니다([공식 문서](https://www.palantir.com/docs/foundry/interfaces/implement-interface)).\
  이 환경에서는 Edit-only 속성인 `viewerGroupIds`도 문제없이 연결됐습니다(화면에는 *Fulfilled by*로 표시되며 아래 '함정 2'의 스크린샷 위쪽에서 볼 수 있습니다).
- **누가 볼 수 있는지 계산하는 로직은 Interface로 합치지 않습니다.**\
  프로젝트는 프로젝트 단위 권한으로, 세부 항목은 프로젝트와 항목 범위로 계산하듯 타입마다 규칙이 달라서 계산 로직은 타입별 함수에 그대로 두었습니다.

정리하면 Interface는 <strong>"권한 값을 담는 칸이 어디에 있는가"</strong>만 하나로 통일하고 <strong>"그 칸에 어떤 값을 넣을 것인가"</strong>는 기존 로직이 계속 정합니다.

### 읽기: Interface 조회 한 번으로 권한 점검

OSDK 클라이언트에 오브젝트 타입 대신 Interface를 넘기면 그 Interface를 구현한 모든 타입의 객체를 한 번에 조회합니다.\
각 객체의 실제 타입은 `$objectType` 필드로 알 수 있습니다.\
TypeScript Functions에서는 함수가 `Client`를 인자로 받고 Ontology에서 자동 생성한 SDK 패키지에서 `KsSecured`를 가져와 바로 쓰면 됩니다.

```ts
// helpers/viewerData.ts (발췌, 패키지 이름은 예시)
import { Client } from "@osdk/client";
import { KsSecured } from "@keystone/sdk";

export async function auditSecuredObjects(client: Client): Promise<Map<string, { total: number; missing: number }>> {
    // asyncIter()는 페이지를 자동으로 넘기며 객체를 순회합니다. Array.fromAsync는 ES2024 런타임 기능입니다.
    const objects = await Array.fromAsync(client(KsSecured).asyncIter());
    const byType = new Map<string, { total: number; missing: number }>();
    objects.forEach((o) => {
        const entry = byType.get(o.$objectType) ?? { total: 0, missing: 0 };
        entry.total += 1;
        if (o.viewerGroupIds == null) entry.missing += 1;
        byType.set(o.$objectType, entry);
    });
    return byType;
}
```

여기서 중요한 점이 있습니다.\
이 환경에서 **Interface로 조회한 결과는 각 타입의 Object Security Policy를 거친 타입별 조회 결과와 같았습니다.**\
공식 문서도 사용자는 권한이 없는 객체와 속성 값을 읽을 수 없다고 설명합니다([공식 문서](https://www.palantir.com/docs/foundry/object-permissioning/object-security-policies)).\
`viewerGroupIds`가 비어 있는 객체는 관리자 그룹(`ks-app-admin`) 조건으로만 보이므로 **누락 점검 함수는 관리자 권한으로 실행해야** 제대로 된 결과가 나옵니다.\
일반 사용자 계정으로 실행하면 권한 값이 빈 객체가 아예 조회되지 않아 누락 건수가 늘 `0`으로 나옵니다.

또 위 코드는 객체를 모두 읽어 와 메모리에서 세므로 대상 객체가 많아지면 그만큼 오래 걸립니다.\
[Interfaces 공식 문서](https://www.palantir.com/docs/foundry/interfaces/interface-overview)에도 Interface 기준 집계(Aggregation)는 아직 개발 중이라고 적혀 있습니다.

검증용 React 웹 앱에도 같은 조회를 붙여 Interface로 조회한 결과와 6개 타입을 하나씩 조회한 결과를 나란히 비교했습니다.

<PostFigure src={webSecuredPage} alt="웹 앱의 권한 대상 Interface 화면. 6개 타입 모두 interface 조회 수와 타입 직접 조회 수가 같고 권한 값 없음은 0, 합계 60">관리자 계정으로 본 Main 브랜치 결과입니다.<br />6개 타입 모두 Interface 조회 건수와 타입별 직접 조회 건수가 같고 권한 값이 빈 객체는 0건입니다.<br /><em>내 그룹으로 보임</em> 열은 로그인한 사용자의 그룹이 <code>viewerGroupIds</code>에 들어 있는 객체 수입니다.</PostFigure>

### 쓰기: 실제 타입을 몰라도 되는 편집

[TypeScript Functions v2](https://www.palantir.com/docs/foundry/functions/typescript-v2-ontology-edits)는 `Edits.Object`와 함께 `Edits.Interface` 타입을 지원하므로 Interface를 거쳐 속성을 고칠 수 있습니다.\
함수 안에서 `createEditBatch`로 배치를 만들어 수정 사항을 담고 `batch.getEdits()`를 돌려주면 그 함수를 실행한 Action이 변경 사항을 Ontology에 반영합니다.

공식 문서의 예제는 Interface로 조회한 객체를 그대로 `batch.update()`에 넘깁니다.\
하지만 제 코드는 권한을 계산하려고 이미 타입별로 조회해 둔 객체를 다시 써야 했습니다.\
그래서 Interface 이름(`$apiName`)과 실제 오브젝트 타입(`$objectType`)과 기본 키(`$primaryKey`)를 묶어 **Interface Locator 객체**를 직접 만들어 넘겼습니다.\
(이 Locator 구조는 공식 문서에 나와 있지 않아 이 환경의 코드와 단위 테스트로 직접 확인했습니다.)

```ts
// helpers/viewerData.ts (발췌)
import { Osdk } from "@osdk/client";
import { EditBatch, Edits } from "@osdk/functions";
import { KsSecured } from "@keystone/sdk";

export type ViewerEdit = Edits.Interface<KsSecured>;

/** viewerGroupIds를 가진 객체의 공통 인터페이스 (6개 타입 공통 구조) */
export interface SecuredObject {
    readonly $apiName: string;
    readonly $primaryKey: string;
    readonly viewerGroupIds?: readonly string[];
}

/** 함수마다 다른 편집 타입과 조합해 쓰므로 update 메서드만 요구합니다 */
type ViewerEditSink = Pick<EditBatch<ViewerEdit>, "update">;

export function securedRef(object: SecuredObject) {
    return {
        $apiName: KsSecured.apiName,
        // 구현하지 않은 타입을 넘겨도 타입 단언 때문에 컴파일은 통과하므로 호출부에서 6개 구현 타입만 넘기도록 주의합니다
        $objectType: object.$apiName as Osdk.Instance<KsSecured>["$objectType"],
        $primaryKey: object.$primaryKey,
    };
}

export function setViewerGroupIds(batch: ViewerEditSink, object: SecuredObject, viewerGroupIds: string[]): void {
    batch.update(securedRef(object), { viewerGroupIds });
}
```

이 헬퍼 덕분에 백필 함수(`resyncKsViewerGroups`)가 간단해집니다.\
누가 어떤 객체를 볼 수 있는지 계산하는 단계(`planViewerUpdates`)는 기존 타입별 규칙을 그대로 쓰고 계산 결과를 반영하는 단계(`applyViewerPlan`)만 Interface 편집으로 처리합니다.

```ts
// functions/resyncKsViewerGroups.ts (발췌)
import { Client } from "@osdk/client";
import { createEditBatch, Edits } from "@osdk/functions";
import { KsGrant } from "@keystone/sdk";
// ViewerEdit, requireGlobalFunction, KS_FUNCTION, loadActiveGrantRules, planViewerUpdates, applyViewerPlan, ALL은 레포 내부 헬퍼입니다

// 부여·회수 함수와 동일한 편집 유니온 타입 (권한 부여 기록 생성은 타입별 편집, 권한 값 갱신은 Interface 편집)
type OntologyEdit = Edits.Object<KsGrant> | ViewerEdit;

export default async function resyncKsViewerGroups(client: Client): Promise<OntologyEdit[]> {
    await requireGlobalFunction(client, KS_FUNCTION.grantEdit); // 권한 관리 기능이 있는 사용자만 실행 가능
    const grants = await loadActiveGrantRules(client);
    const batch = createEditBatch<OntologyEdit>(client);
    applyViewerPlan(batch, await planViewerUpdates(client, grants, ALL)); // 변경된 객체마다 setViewerGroupIds 호출
    return batch.getEdits();
}
```

이렇게 만든 편집은 `updateObjectForInterface` 형식으로 나갑니다.\
단위 테스트에서는 타입이 다른 두 객체(`KsProject`와 `KsGrant`)를 고쳐도 같은 `updateObjectForInterface` 편집 두 개가 만들어지는 것을 확인했습니다.

```ts
// __tests__/ksPermissions.test.ts (발췌)
// edits = 백필 함수가 반환한 편집 목록
expect(edits.map((e) => e.type)).toEqual(["updateObjectForInterface", "updateObjectForInterface"]);
expect(edits.map((e) => e.obj)).toEqual([
    { $apiName: "KsSecured", $objectType: "KsProject", $primaryKey: "KS-PJ-001" },
    { $apiName: "KsSecured", $objectType: "KsGrant", $primaryKey: "KS-G-001" },
]);
```

참고로 공식 문서는 Interface를 거친 객체 생성(`create`)도 소개하지만 이때는 Interface 속성 중 하나가 기본 키(Primary Key)에 연결되어 있어야 합니다.\
`KsSecured`에는 `viewerGroupIds` 하나뿐이므로 객체 생성은 기존처럼 타입별 편집(`Edits.Object`)으로 두었습니다.

### 다른 방법과 비교

| 방법 | 누락 점검(읽기) | 권한 갱신(쓰기) | 새 권한 타입을 추가할 때 | 특징과 비용 |
|---|---|---|---|---|
| **타입별 조회·편집 나열** | 타입 수만큼 따로 조회 | 타입별 `Edits.Object` 나열 | 조회·편집 코드와 계산 규칙에 모두 타입 추가 | 가장 단순하지만 코드 중복이 많음 |
| **TypeScript 제네릭 함수만 사용** | 여전히 타입마다 따로 조회 | 함수 시그니처에 타입별 편집 유니온이 남음 | 조회·편집 코드와 계산 규칙에 타입 추가 | 병합 한 번으로 끝나고 플랫폼 설정을 더하지 않음 |
| **Ontology Interface 도입** | **Interface 조회 한 번** | **`Edits.Interface` 하나로 통일**<br />(객체 생성은 타입별 유지) | Interface 구현 연결 + 설정 켜기 + 계산 규칙 추가 | 병합 두 번<br />타입별 설정과 인덱싱 대기<br />병합 뒤 앱 리소스 등록 |

코드 중복만 줄이려면 TypeScript 제네릭 함수로도 상당 부분 해결되고 Foundry 설정을 건드릴 필요도 없습니다.\
하지만 플랫폼이 타입을 하나로 묶어 주지 않으므로 전체 점검 조회와 함수 반환 타입 선언에는 여전히 모든 타입을 나열해야 합니다.\
Ontology Interface는 이 묶음을 플랫폼에 선언하는 대신 이어서 설명할 두 함정을 넘어야 합니다.

## 함정 1: 브랜치에서 새로 만든 Interface로 편집하는 함수가 실패했다

이 환경에서는 모든 Ontology 변경을 Global Branch에서 하고 Proposal로 병합합니다(`Main` 브랜치는 보호되어 있습니다).\
그래서 처음에는 브랜치 하나(`ks-interface-v1`)에서 `KsSecured`를 새로 만들고 읽기 코드와 쓰기 코드를 한꺼번에 넣어 병합하려고 했습니다.

읽기 코드는 잘 동작했지만 **Interface로 편집(`Edits.Interface`)하는 함수는 두 곳에서 실패**했습니다.

| 실패한 곳 | 오류 메시지 |
|---|---|
| 코드 레포 CI의 함수 탐색 단계 (`typescriptDiscoverFunctions`) | `"OntologyEdit" is not a supported type` |
| 브랜치 미리보기 실행 (`rune execute --branch-rid <Global Branch RID>`) | `Conjure error STATUS 400` (`getObjectTypesForInterfaceTypes`) |

첫 번째 오류에 나온 `OntologyEdit`는 함수가 돌려주는 편집 목록의 타입 별칭(`Edits.Object<…> | Edits.Interface<KsSecured>`)입니다.\
별칭 이름이 문제가 아니라 그 안의 `Edits.Interface<KsSecured>`를 CI 함수 탐색이 해석하지 못해서 생긴 오류였습니다.

원인을 따라가 보니 이랬습니다.

- **CI 함수 탐색이 실패한 이유**: CI 함수 탐색은 빌드 중에 만들어지는 `build/entityMetadataMapping.json` 파일의 `interfaceTypes` 목록에서 Interface를 찾습니다.\
  그런데 **Main에 아직 병합되지 않고 브랜치에만 있는 새 Interface는 브랜치 CI 빌드에서도 이 목록에 들어가지 않았습니다.**\
  로컬에서 이 JSON 파일에 `KsSecured` 항목 한 줄을 직접 넣고 탐색 도구를 돌리자 통과했습니다.
- **미리보기 실행이 400으로 실패한 이유**: 오류가 난 API 이름(`getObjectTypesForInterfaceTypes`)으로 미루어 함수 런타임이 Interface의 구현 타입 목록을 브랜치 정보 없이 조회하는 것으로 보입니다.\
  `functions runtime` 0.351과 0.357에서 똑같이 재현됐습니다.

더 헷갈렸던 것은 **로컬에서 실행한 `./rune discover`는 오류 없이 통과했다**는 점입니다.\
로컬 `rune`은 브랜치 기준으로 생성한 SDK 메타데이터를 보고 Interface를 찾았기 때문입니다.\
로컬 `rune discover`가 통과해도 CI 통과를 뜻하지 않았으므로 이 환경에서는 Gradle 빌드로 `build/entityMetadataMapping.json`을 만든 뒤 레포 루트에서 탐색 도구를 직접 돌려 CI와 같은 조건으로 확인했습니다.

```bash
typescript-functions/node_modules/.bin/discovery discoverOsdkFunctions "$PWD" out.json \
  --entityMetadataMappingFilePath typescript-functions/build/entityMetadataMapping.json
```

*(참고: Main에 이미 있는 Interface에 브랜치에서 구현 타입이나 속성을 새로 추가하는 경우는 테스트하지 않았습니다.)*

### 해결: 두 번에 나눠 병합

Interface 조회(읽기)는 브랜치에서도 잘 동작했으므로 작업을 두 번의 병합으로 나눴습니다.

1. **1단계 브랜치 (`ks-interface-v1`)**: `KsSecured` 정의와 6개 타입의 구현 연결, 읽기(점검) 함수, 툴체인 업그레이드만 넣습니다.\
   쓰기 코드는 기존 타입별 편집(`Edits.Object`)을 그대로 두고 먼저 Main에 병합합니다.
2. **2단계 브랜치 (`ks-interface-v2`)**: `KsSecured`가 Main에 생긴 뒤 쓰기 코드를 `Edits.Interface`로 바꿉니다.\
   CI 통과를 확인하고 병합합니다.

<PostFigure src={proposalInterfaceCreated} alt="Global Branching Proposal 화면. 병합된 리소스에 오브젝트 타입 6개와 Created 표시가 붙은 Ks Secured interface, keystone-functions 레포가 있다">1단계 Proposal 화면입니다.<br />구현을 추가한 오브젝트 타입 6개와 새로 만든 Interface(Created)와 함수 레포가 함께 Main에 병합됩니다.</PostFigure>

1단계를 Main에 병합하고 2단계 브랜치를 열자 로컬 Gradle 빌드가 만든 `entityMetadataMapping.json`에 `KsSecured`가 들어갔고 CI도 통과했습니다.\
1단계에서 400 오류가 났던 브랜치 미리보기 실행도 성공했습니다.

1단계를 병합해도 기존 Main의 Action 동작은 바뀌지 않았습니다.\
[함수 기반 Action](https://www.palantir.com/docs/foundry/action-types/function-actions-getting-started)은 Rules 탭에서 지정한 함수 버전을 쓰고 자동 업그레이드(Auto upgrade)를 켜면 호환되는 Minor·Patch 버전을 자동으로 따라갑니다.\
이 환경의 Main에서는 부여·회수 Action이 `2.0.1`, 백필 Action이 `2.2.0`을 가리켰고(저장 내용상 그 패치 하나만 받는 범위) 자동 업그레이드도 꺼져 있었습니다.\
그래서 1단계 병합으로 `2.3.0` 함수가 발행되어도 기존 Action은 영향을 받지 않았습니다.\
자동 업그레이드를 켜 두었다면 병합하자마자 새 함수 버전이 적용될 수 있으므로 미리 확인해야 합니다.

## 함정 2: 구현 타입마다 'Enable interface actions'를 켜야 했다

2단계 브랜치에서 CI와 브랜치 미리보기 실행이 모두 통과해서 이제 끝났다고 생각했습니다.\
그런데 브랜치 테스트에서 권한 부여 Action을 실행하자 바로 아래 오류로 실패했습니다.

```text
ApplyActionFailed
Actions:FunctionEditsInterfaceActionsDisabledObjectTypes
```

함수가 Interface Locator로 객체를 고치려 했지만 대상 오브젝트 타입들에서 Interface Action 허용 설정이 꺼져 있다는 뜻의 메시지였습니다.

원인은 오브젝트 타입마다 있는 토글 하나였습니다.\
Ontology Manager에서 오브젝트 타입을 열고 **Interfaces 탭 → Interface action control**에 있는 ***Enable interface actions***를 켜야 합니다.\
검증 환경의 6개 타입은 모두 이 토글이 기본으로 꺼져 있었습니다.\
토글을 켜면 Interface Action 타입의 제출 조건(Submission criteria)이 모든 구현 타입에 똑같이 적용된다는 안내가 함께 나옵니다.

<PostFigure src={objectTypeInterfacesTab} alt="오브젝트 타입 Ks Grant의 Interfaces 탭. Viewer Group Ids가 Viewer Group Ids로 채워져 있고 Interface action control에 Enable interface actions 토글이 켜져 있다">오브젝트 타입 → Interfaces 탭 화면입니다.<br />위쪽은 Interface 속성을 기존 속성에 연결한 부분(<em>Fulfilled by</em>)이고 아래쪽이 <em>Enable interface actions</em> 토글과 안내 문구입니다.</PostFigure>

여기서 [공식 문서](https://www.palantir.com/docs/foundry/action-types/actions-on-interfaces)의 설명과 이 환경에서 본 동작을 나란히 놓으면 헷갈리는 부분이 있습니다.\
공식 문서는 Interface Action 타입의 제출 조건과 권한이 모든 구현 타입에 똑같이 적용되고 *Interface action control*에서 타입별로 끌 수 있다고 설명합니다.\
같은 문서는 Interface Action 타입을 함수(Function)와 함께 쓸 수 없다고도 적고 있습니다.

제가 만든 Action은 Interface Action 타입이 아니라 **일반 함수 기반 Action**입니다.\
그런데도 이 환경에서는 **함수 안에서 Interface Locator(`Edits.Interface`)로 객체를 고치자 Action 실행 단계에서 이 설정(*Enable interface actions*)에 걸렸습니다.**

이 함정을 늦게 발견한 이유는 두 가지입니다.

- **함수 탐색과 CI와 브랜치 미리보기 실행은 이 설정에 걸리지 않았습니다.**\
  미리보기 실행은 Action을 거치지 않고 편집을 실제로 적용하지도 않으므로 이 설정을 확인할 수 없었습니다([공식 문서](https://www.palantir.com/docs/foundry/functions/typescript-v2-ontology-edits)).
- **앞서 실행한 백필 Action 테스트는 설정이 꺼진 상태에서도 통과했습니다.**\
  모든 객체의 권한 값이 이미 맞아서 백필 함수가 돌려준 편집이 **0건**이었기 때문입니다.\
  이 환경에서는 편집이 0건인 실행은 이 검사에 걸리지 않았습니다.

그러니 테스트는 <strong>객체 값이 실제로 바뀌는 시나리오(권한 부여·회수)</strong>로 해야 합니다.\
6개 타입 모두에서 *Enable interface actions*를 켜고 브랜치에 저장하자 이미 인덱싱되어 있던 `KsGrant`를 뺀 5개 타입의 브랜치 인덱싱이 시작됐습니다.\
인덱싱이 끝난 뒤에야 부여·회수 테스트가 모두 통과했습니다.

하나 더 있습니다.\
Action을 저장할 때 Foundry가 "아직 인덱싱되지 않은 오브젝트 타입을 수정합니다"라고 알려 준 대상은 함수가 타입별 편집(`Edits.Object`)으로 직접 고치는 `KsGrant` 하나뿐이었습니다.\
`Edits.Interface`로 고치는 나머지 5개 타입은 이 경고 목록에 나오지 않아서 저장 화면만 보고는 이 설정이나 인덱싱이 필요하다는 것을 알아채기 어려웠습니다.

정리하면 이 환경에서는 Interface 편집을 쓰려면 구현 타입마다 이 토글을 켜야 했습니다.\
그러니 **이 Interface로 권한 값을 고치는 모든 Action의 제출 조건과 권한도 함께 점검**하는 것이 안전합니다.\
제 환경에서는 백필 Action의 제출 조건을 관리자 그룹으로 제한했고 부여·회수·백필 함수 안에서도 호출한 사용자가 권한 관리 기능을 가졌는지 한 번 더 확인합니다(부여·회수 Action의 제출 조건은 이 글에서 다루지 않습니다).\
공식 문서도 Interface 권한은 Ontology 역할로 관리되며 Interface Action으로 객체를 만들고 고치고 지울 수 있는 사용자를 신중히 검토하라고 안내합니다([Interface 공식 문서](https://www.palantir.com/docs/foundry/interfaces/interface-overview), [Action 공식 문서](https://www.palantir.com/docs/foundry/action-types/actions-on-interfaces)).

## 그 밖에 걸린 것

### 1. 브랜치에서 함수 버전 태그를 발행해야 Proposal을 병합할 수 있었다

1단계 Proposal을 병합하려고 하자 함수 레포 검사가 *Function version target not set* 오류로 막혔습니다.\
그 브랜치에서 발행한 함수 버전이 없었기 때문입니다.

Foundry의 함수 버전은 [Semantic Versioning](https://www.palantir.com/docs/foundry/functions/functions-versioning)을 따르며 Patch·Minor·Major 단위로 올립니다.\
코드 레포의 **Tags → New tag**에서 Branch를 작업 중인 Global Branch로 고르고 Minor를 선택해 태그를 발행하자 레포 검사가 통과했습니다.\
이후 Proposal을 병합하니 코드 레포 `master` 브랜치에 정식 버전 태그(`2.3.0`)가 붙었습니다.

<PostFigure src={repoNewTagDialog} alt="코드 레포의 Tag and release 대화상자. 브랜치 선택과 Stable, Prerelease 옵션, Patch 2.4.1, Minor 2.5.0, Major 3.0.0 선택지가 보인다">코드 레포 → Tags → New tag 대화상자입니다.<br />2단계 병합까지 마친 뒤 master에서 다시 캡처해서 최신 태그가 2.4.0으로 보입니다.<br />Proposal 병합을 위해 발행할 때는 여기서 Branch를 작업 중인 Global Branch로 바꿔 태그를 발행합니다.</PostFigure>

2단계 브랜치에서는 새 함수 버전(`2.4.0`)을 발행한 뒤 권한 부여·회수·백필 Action의 Rules에서 함수 버전을 `2.4.0`으로 직접 바꿔 저장했습니다.

<PostFigure src={actionRulesFunctionVersion} alt="Grant Ks Permission Action 타입의 Rules 화면. Run function 규칙의 함수 grantKsPermission과 버전 2.4.0, 꺼진 Auto upgrade 토글이 보인다">Action 타입 → Rules 화면입니다.<br />함수 이름 아래에 버전 선택 목록(2.4.0)과 <em>Auto upgrade to compatible versions</em> 토글이 있습니다.</PostFigure>

### 2. 웹 앱 리소스는 Main에 병합한 뒤에야 추가할 수 있었다

검증용 React 웹 앱은 Developer Console에 등록한 앱으로 로그인한 사용자의 토큰을 쓰고 이 앱은 <strong>리소스 제한 모드(Application restrictions)</strong>입니다.\
제한 모드 앱은 Developer Console의 Ontology SDK 탭에 등록한 오브젝트 타입과 Interface와 Action에만 접근할 수 있습니다([공식 문서](https://www.palantir.com/docs/foundry/developer-console/application-restrictions)).

1단계 브랜치 작업 중 웹 앱에서 새로 만든 `KsSecured` 조회와 백필 Action 호출을 시도하자 `404 Not Found` 오류가 났습니다.\
Developer Console의 앱은 Global Branch 바깥에 있어서 아직 브랜치에만 있는 Interface를 앱의 허용 리소스에 추가할 수 없었습니다.\
결국 1단계 Proposal을 Main에 병합한 뒤에야 Developer Console에서 `KsSecured`와 관련 Action을 리소스에 등록하고 웹 앱 연동을 마쳤습니다.

<PostFigure src={devConsoleSdkResources} alt="Developer Console의 Ontology SDK Resources 화면. Action types에 권한 부여, 백필, 회수 Action이 보이고 Interfaces 섹션에 Ks Secured가 있다">Developer Console → 앱 → Ontology SDK → Resources 화면입니다.<br />1단계 병합 뒤 Interfaces에 Ks Secured를 추가했습니다(관계없는 Action 항목은 가렸습니다).</PostFigure>

### 3. `VALIDATE_ONLY`와 `returnEdits`를 함께 보내면 400 오류가 났다

웹 앱의 'Action 사전 검증(Dry-run)' 버튼을 누르자 `400 InvalidApplyActionOptionCombination` 오류가 돌아왔습니다.\
[Apply Action API](https://www.palantir.com/docs/foundry/api/ontologies-v2-resources/actions/apply-action)의 `options`에는 실행 방식을 정하는 `mode`(`VALIDATE_ONLY` 또는 `VALIDATE_AND_EXECUTE`)와 편집 내역을 돌려받을지 정하는 `returnEdits`가 있습니다.\
이 환경에서는 `mode: "VALIDATE_ONLY"`와 `returnEdits`를 함께 보내면 옵션 조합 오류로 거부됐습니다.\
사전 검증 요청에서는 `returnEdits`를 빼고 `mode`만 보내도록 고쳐 해결했습니다.

## 검증 결과

변경 전후가 맞는지 확인하려고 REST API를 호출하는 Python 검증 스크립트를 만들었습니다.\
같은 사용자 토큰으로 **Interface로 한꺼번에 조회한 결과**와 **6개 타입을 하나씩 조회한 결과**(객체 집합과 각 객체의 `viewerGroupIds` 값)가 똑같은지 비교했습니다.\
2단계에서는 권한 부여·회수·백필 Action의 실행 결과와 Main에 영향이 없는지도 함께 확인했습니다.

| 검증 단계 | 결과 (통과 항목 수 / 전체 항목 수) |
|---|---|
| 1단계 브랜치 테스트 | **7 / 7 통과** |
| 1단계 Proposal 병합 | 함수 버전 `2.3.0` 정식 발행 |
| 2단계 브랜치 1차 테스트 | **6 / 10 통과**<br />권한 부여 Action이 '함정 2'의 설정 누락으로 실패 |
| *Enable interface actions*를 켠 뒤 2차 테스트 | **12 / 12 통과** |
| 2단계 Proposal 병합 | 함수 버전 `2.4.0` 정식 발행 |
| 2단계 병합 뒤 Main 최종 점검 | **7 / 7 통과** |

- **Main 점검**: 관리자 계정은 모두 60건(`KsLineItem` 31건, `KsRevisionSnapshot` 10건, `KsRevision` 6건, `KsGrant` 5건, `KsProject` 4건, `KsDocument` 4건)을 조회했고 일반 사용자인 팀 A 계정은 33건을 조회했습니다.\
  두 계정 모두 Interface 조회 결과와 타입별 조회 결과가 완전히 같았고 권한 값이 빈(`null`) 객체는 0건이었습니다.\
  1단계 병합 직후와 숫자가 같아서 쓰기를 Interface로 바꾼 뒤에도 권한 값이 달라지지 않았음을 확인했습니다.
- **2차 브랜치 부여·회수 테스트**: 팀 B에게 프로젝트 1건의 접근 권한을 부여하자 권한 기록(`KsGrant`) 1건이 새로 생기고 관련 객체 11개의 `viewerGroupIds`에 팀 B가 추가됐습니다.\
  이어서 권한을 회수하자 객체 12개(관련 객체 11개와 상태가 바뀐 권한 기록 1개)가 수정되어 처음 상태로 돌아왔습니다.
- **편집 형식 확인**: 이 환경의 REST API `returnEdits` 응답에서는 Interface를 거친 편집도 실제 오브젝트 타입의 수정으로 보였습니다.\
  그래서 함수가 Interface 편집(`updateObjectForInterface`)을 만들었는지는 앞에서 본 단위 테스트로 확인했습니다.

## 실무 적용 체크리스트

여러 오브젝트 타입에 흩어진 권한 속성을 Ontology Interface로 묶으려는 분께 권하는 순서입니다.

### 1단계 브랜치 (정의와 읽기)

1. **Interface 정의와 구현 연결**: 권한 속성이 있는 모든 오브젝트 타입에서 Interface를 구현하고 Interface 속성을 각 타입의 기존 권한 속성에 연결(*Fulfilled by*)합니다.
2. **통합 점검 쿼리**: Interface 조회 한 번으로 타입별 전체 객체 수와 권한 값이 빈 객체 수를 세는 점검 함수를 만듭니다.\
   (빈 객체를 보려면 관리자 권한으로 실행해야 합니다.)
3. **쓰기는 그대로**: 아직 Interface가 Main에 없으므로 `Edits.Interface` 쓰기 코드는 넣지 않습니다.
4. **함수 버전 발행과 Action 설정 확인**: 작업 브랜치에서 새 함수 버전 태그를 발행합니다.\
   이때 Main의 기존 Action이 자동 업그레이드(Auto upgrade)로 새 버전을 바로 쓰지 않는지 미리 확인합니다.

### 1단계 병합 직후

5. **Developer Console 앱 리소스 등록**: 웹 앱이 리소스 제한 모드라면 Main에 병합된 새 Interface와 관련 Action을 앱 리소스에 추가합니다.

### 2단계 브랜치 (쓰기 전환과 설정)

6. **쓰기를 Interface 편집으로 전환**: 함수의 편집 코드를 `Edits.Interface`로 바꾸고 CI 함수 탐색이 통과하는지 확인합니다.
7. ***Enable interface actions* 켜기**: Interface를 구현한 모든 오브젝트 타입의 *Interfaces* 탭에서 이 토글을 켜고 그 타입들의 브랜치 인덱싱이 끝날 때까지 기다립니다.
8. **Action 제출 조건 점검**: Interface로 권한 값을 고치는 모든 Action의 제출 조건이 관리자 그룹으로 제한되어 있는지와 Interface를 편집할 수 있는 사람이 누구인지 확인합니다.
9. **Action의 함수 버전 변경**: 관련 Action이 2단계 브랜치에서 새로 발행한 함수 버전을 가리키도록 바꿉니다.
10. **값이 실제로 바뀌는 테스트**: 편집이 0건인 실행만으로는 *Enable interface actions* 누락이 드러나지 않았으므로 객체 값이 실제로 바뀌는 권한 부여·회수로 테스트합니다.

### 2단계 병합 직후

11. **Main 최종 확인**: Main에서 모든 구현 타입의 인덱싱 완료와 *Enable interface actions* 상태와 Action의 함수 버전을 확인한 뒤 통합 점검 쿼리를 실행합니다.\
    (Main 인덱싱이 끝나기 전에 권한 부여·회수를 실행하는 경우는 검증하지 않았으므로 인덱싱이 끝난 것을 확인한 뒤 실행하는 것이 안전합니다.)

## 마무리

Ontology Interface는 <strong>"여러 오브젝트 타입이 같은 의미와 모양의 속성을 공유한다"</strong>는 사실을 플랫폼에 선언하는 도구입니다.\
행 권한 속성처럼 여러 타입에 똑같이 반복되는 값이라면 읽기와 쓰기에서 타입별 분기 코드를 크게 줄일 수 있습니다(계산 규칙과 객체 생성은 타입별로 남습니다).\
도입한 Interface 구현을 다시 걷어 내는 경우는 테스트하지 않았습니다.
