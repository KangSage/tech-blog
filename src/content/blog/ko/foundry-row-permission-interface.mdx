<summary>이 글을 쓰게 된 이유</summary>

Foundry로 실무 프로젝트를 준비하면서 개인 개발자 티어에 작은 검증용 환경(`Keystone PoC`)을 만들어 쓰고 있습니다.\
글에 나오는 `Ks…`로 시작하는 이름은 모두 이 검증 환경에서 붙인 예시 이름이고 데이터도 전부 가상입니다.\
권한 값을 가진 타입 중 4개는 글에서 일반적인 이름으로 바꿔 적었고 스크린샷에서는 그 이름을 가렸습니다.

이번에는 2026년 10월 16일 새벽부터 낮까지 행 단위 권한 값을 다루는 코드를 Ontology Interface 하나로 모았습니다.\
설계 자체는 단순했지만 브랜치와 설정에서 두 번 걸려 넘어졌습니다.\
같은 작업을 하려는 분들이 같은 곳에서 시간을 쓰지 않도록 기록으로 남깁니다.

</details>

Foundry에서 행 단위 권한을 걸면 권한 값을 가진 오브젝트 타입이 금방 여러 개로 늘어납니다.\
제 환경에서는 6개 타입이 같은 이름의 권한 속성 `viewerGroupIds`를 각자 들고 있었고 그 값을 점검하거나 고치는 코드도 타입마다 따로 써야 했습니다.\
이 글은 그 속성을 **interface 하나로 묶어 한 곳에서 읽고 쓰게 바꾼 과정**을 다룹니다.

결과부터 말하면 권한 값이 빠진 객체를 찾는 점검은 interface 조회 한 번으로 줄었고 권한 값을 쓰는 코드는 객체의 타입을 몰라도 됩니다.\
새 권한 타입이 생기면 interface를 구현하는 것만으로 점검 대상에 들어갑니다.\
다만 누가 볼 수 있는지 계산하는 규칙은 타입마다 따로 추가해야 합니다.

대가도 있습니다.\
Foundry 쪽 작업이 두 번의 병합으로 나뉘고 구현 타입마다 켜야 하는 설정이 하나 늘어납니다.\
브랜치에서 타입이나 Action을 바꾸면 그 타입의 브랜치 인덱싱도 기다려야 했습니다.\
이 환경에서는 Action을 저장한 뒤 타입 하나의 인덱싱에 약 10분 걸린 적이 있습니다.\
이 환경에서는 *Enable interface actions*를 켜야 interface를 거친 편집이 적용됐으므로 권한 값을 쓰는 Action의 제출 조건도 함께 확인하는 것이 좋습니다.

그리고 두 가지 함정이 있었습니다.\
첫째, 이 환경에서는 브랜치에서 새로 만든 interface로 **편집**하는 함수가 CI와 브랜치 미리보기 실행 모두에서 실패했습니다.\
그래서 interface 정의를 먼저 병합하고 그 interface를 쓰는 코드를 다음 브랜치에서 병합했습니다.\
둘째, 구현 타입마다 *Enable interface actions*를 켜지 않으면 Action 실행 단계에서야 실패했습니다.

## 배경: 행 권한이 걸린 6개 타입

먼저 이 글에 나오는 Foundry 용어를 짧게 정리합니다.

- **오브젝트 타입(Object type)**: Ontology에서 업무 대상 하나를 나타내는 타입입니다.\
  테이블 하나에 대응하는 모델 클래스로 생각하면 가깝습니다.
- **object security policy**: 오브젝트 타입에 거는 행 단위 권한 규칙입니다.\
  사용자 속성(그룹 ID 등)을 객체의 속성과 비교하는 granular policy로 그 행을 보여 줄지 정합니다([문서](https://www.palantir.com/docs/foundry/object-permissioning/object-security-policies), [granular policy](https://www.palantir.com/docs/foundry/platform-security-management/manage-granular-policies)).
- **Action**: Ontology의 객체를 바꾸는 정해진 작업입니다.\
  이 글의 Action은 모두 TypeScript 함수가 편집 내용을 만들고 Action이 그 편집을 적용하는 함수 기반 Action입니다.
- **edit-only 속성**: 백킹 데이터셋 컬럼에 연결하지 않고 Ontology 편집으로만 값을 넣는 속성입니다.\
  Object Storage V2 타입에서만 쓸 수 있고 속성 자체의 권한은 백킹 데이터셋 중 하나에 맞춰야 합니다([문서](https://www.palantir.com/docs/foundry/object-link-types/edit-only-properties)).
- **Global Branching**: Ontology와 코드 레포를 함께 브랜치에서 바꾸고 Proposal로 Main에 병합하는 기능입니다([문서](https://www.palantir.com/docs/foundry/global-branching/core-concepts)).\
  코드 레포의 기본 브랜치 이름은 master이고 Ontology 쪽 기본 브랜치는 Main으로 부릅니다.
- **브랜치 인덱싱**: 브랜치에서 정의를 바꾸거나 Action으로 수정할 오브젝트 타입을 그 브랜치에서 조회·편집할 수 있게 색인하는 작업입니다.\
  이 환경에서는 인덱싱이 끝나기 전에는 그 타입을 바꾸는 Action을 브랜치에서 실행할 수 없었습니다.
- **OSDK와 rune**: OSDK는 Ontology에서 생성한 타입으로 객체를 다루는 TypeScript SDK입니다([문서](https://www.palantir.com/docs/foundry/ontology-sdk/typescript-osdk)).\
  rune은 이 환경의 TypeScript Functions 레포 템플릿에 들어 있는 CLI로 로컬에서 함수를 탐색하고 실행할 때 썼습니다.
- **함수 탐색(discovery)**: 함수 레포를 빌드할 때 어떤 함수가 있고 어떤 타입을 읽고 편집하는지 찾아 등록하는 단계입니다.
- **백필(backfill)**: 비어 있거나 틀린 권한 값을 규칙대로 다시 채우는 작업입니다.

검증 환경의 행 권한은 이렇게 동작합니다.\
6개 타입이 모두 `viewerGroupIds`라는 그룹 ID 목록 속성을 가집니다.

| 타입 | 설명 |
|---|---|
| `KsProject` | 프로젝트 |
| `KsDocument` | 프로젝트 아래의 문서 |
| `KsRevision` | 문서의 작업본·리비전 |
| `KsRevisionSnapshot` | 리비전에 딸린 참조 사본 |
| `KsLineItem` | 세부 항목 |
| `KsGrant` | 권한 부여 기록 |

각 타입의 object security policy는 **사용자가 속한 그룹과 `viewerGroupIds`가 하나라도 겹치거나 사용자가 어드민 그룹 `ks-app-admin`에 속하면** 그 행을 보여 줍니다.

`viewerGroupIds`는 edit-only 속성입니다.\
데이터셋을 다시 빌드해도 권한 값이 덮이지 않게 하려고 이렇게 바꿨습니다.

그 대신 값이 비어 있는(null) 객체는 일반 사용자에게 보이지 않습니다.\
transform이 새 행을 만들면 그 행은 권한 값이 비어 있으므로 Action으로 값을 채워야 합니다(조건에 따라 Action을 자동 실행하는 Automate를 쓸 수도 있습니다).\
실무에서도 원천 데이터가 transform으로 들어오는 타입이라면 같은 상황이 생깁니다.

여기서 두 가지 일이 반복됩니다.

1. **점검**: 6개 타입에서 권한 값이 비어 있는 객체가 있는지 확인합니다.
2. **쓰기**: 권한 부여·회수·백필 Action이 바뀐 객체의 `viewerGroupIds`를 고칩니다.

interface를 쓰기 전에는 두 일 모두 6개 타입을 하나씩 조회하고 타입별 편집을 나열하는 코드였습니다.

## 설계: interface `KsSecured`

Ontology Interface는 오브젝트 타입의 모양을 기술하는 Ontology 타입이고 오브젝트 타입이 그것을 구현합니다([문서](https://www.palantir.com/docs/foundry/interfaces/interface-overview)).\
interface 자체로는 객체를 만들 수 없고 객체는 항상 구현한 실제 타입에 속합니다.\
TypeScript의 `interface`와 비슷하게 생각하면 됩니다.

만든 것은 다음과 같습니다.

- interface `KsSecured`에 속성 하나 `viewerGroupIds`를 둡니다.\
  화면에는 표시 이름 *Viewer Group Ids*로 나옵니다.
- 6개 타입이 `KsSecured`를 구현합니다.\
  오브젝트 타입의 *Interfaces* 탭에서 interface를 구현하면서 interface 속성을 각 타입이 이미 가진 속성에 연결합니다([문서](https://www.palantir.com/docs/foundry/interfaces/implement-interface)).\
  이 환경에서는 edit-only 속성 `viewerGroupIds`도 연결할 수 있었습니다(화면 표시는 *Fulfilled by*이고 아래 함정 2의 스크린샷 위쪽에 보입니다).
- **누가 볼 수 있는지 계산하는 규칙은 interface로 묶지 않습니다.**\
  프로젝트는 프로젝트 부여로, 세부 항목은 프로젝트와 항목 범위로 계산하듯 규칙이 타입마다 달라서 그대로 타입별 함수에 남겼습니다.

즉 interface는 "권한 값을 담는 칸이 어디 있는지"만 통일하고 "그 칸에 무엇을 넣을지"는 기존 코드가 계속 정합니다.

### 읽기: interface 조회 한 번으로 점검

OSDK 클라이언트에 interface를 넘기면 구현한 모든 타입의 객체를 한 번에 받습니다.\
각 객체의 실제 타입은 `$objectType`에 들어 있습니다.\
TypeScript Functions에서는 함수가 `Client`를 인자로 받고 `KsSecured`는 레포가 Ontology에서 생성한 SDK 패키지에서 가져옵니다.

```ts
// helpers/viewerData.ts (발췌, 패키지 이름은 예시)
import { Client } from "@osdk/client";
import { KsSecured } from "@keystone/sdk";

export async function auditSecuredObjects(client: Client): Promise<Map<string, { total: number; missing: number }>> {
    // asyncIter()는 페이지를 넘기며 객체를 하나씩 돌려준다. Array.fromAsync는 ES2024 런타임 기능이다
    const objects = await Array.fromAsync(client(KsSecured).asyncIter());
    const byType = new Map<string, { total: number; missing: number }>();
    objects.forEach((o) => {
        const entry = byType.get(o.$objectType) ?? { total: 0, missing: 0 };
        entry.total += 1;
        if (o.viewerGroupIds == null) entry.missing += 1;
        byType.set(o.$objectType, entry);
    });
    return byType;
}
```

조회도 object security policy를 그대로 따릅니다.\
문서도 사용자가 권한 없는 객체와 속성 값은 읽을 수 없다고 설명합니다([문서](https://www.palantir.com/docs/foundry/object-permissioning/object-security-policies)).\
값이 빈 객체는 어드민 그룹 조건으로만 보이므로 **이 점검은 어드민으로 실행해야 의미가 있습니다.**\
일반 사용자가 실행하면 빈 객체가 아예 보이지 않아 항상 0으로 나옵니다.\
이 코드는 객체를 모두 읽어 셉니다.\
Interfaces 문서에도 interface 기준 집계는 아직 개발 중으로 적혀 있습니다([문서](https://www.palantir.com/docs/foundry/interfaces/interface-overview)).\
객체가 많아지면 그만큼 오래 걸립니다.

웹 앱에도 같은 조회를 붙여 interface 조회 결과와 타입별 직접 조회 결과를 나란히 비교했습니다.

### 쓰기: 타입을 몰라도 되는 편집

TypeScript Functions v2는 편집 타입으로 `Edits.Object`와 함께 `Edits.Interface`를 두고 interface를 통한 속성 수정을 지원합니다([문서](https://www.palantir.com/docs/foundry/functions/typescript-v2-ontology-edits)).\
함수는 `createEditBatch`로 편집 배치를 만들고 배치에 편집을 담은 뒤 `batch.getEdits()`를 돌려줍니다.\
Action은 그 편집 목록을 받아 Ontology에 적용합니다.

문서의 예시는 interface로 조회한 객체를 그대로 `update`에 넘깁니다.\
이 코드는 타입별로 조회한 객체를 재사용하므로 interface 이름(`$apiName`)과 실제 타입(`$objectType`)과 기본 키(`$primaryKey`)로 locator를 직접 만들어 넘겼습니다.\
이 locator 모양은 문서가 아니라 이 환경의 코드와 테스트로 확인한 것입니다.

```ts
// helpers/viewerData.ts (발췌)
import { Osdk } from "@osdk/client";
import { EditBatch, Edits } from "@osdk/functions";
import { KsSecured } from "@keystone/sdk";

export type ViewerEdit = Edits.Interface<KsSecured>;

/** viewerGroupIds를 가진 아무 객체 (6개 타입 공통 모양) */
export interface SecuredObject {
    readonly $apiName: string;
    readonly $primaryKey: string;
    readonly viewerGroupIds?: readonly string[];
}

/** 함수마다 다른 편집 타입과 함께 쓰므로 update만 요구한다 */
type ViewerEditSink = Pick<EditBatch<ViewerEdit>, "update">;

export function securedRef(object: SecuredObject) {
    return {
        $apiName: KsSecured.apiName,
        // 구현하지 않은 타입을 넘겨도 컴파일은 되므로 호출하는 쪽이 6개 타입만 넘긴다
        $objectType: object.$apiName as Osdk.Instance<KsSecured>["$objectType"],
        $primaryKey: object.$primaryKey,
    };
}

export function setViewerGroupIds(batch: ViewerEditSink, object: SecuredObject, viewerGroupIds: string[]): void {
    batch.update(securedRef(object), { viewerGroupIds });
}
```

백필 함수는 이 조각들을 이렇게 씁니다.\
계산(`planViewerUpdates`)은 타입별 규칙을 그대로 쓰고 쓰기(`applyViewerPlan`)만 위의 interface 편집으로 나갑니다.

```ts
// functions/resyncKsViewerGroups.ts (발췌)
import { Client } from "@osdk/client";
import { createEditBatch, Edits } from "@osdk/functions";
import { KsGrant } from "@keystone/sdk";
// ViewerEdit, requireGlobalFunction, KS_FUNCTION, loadActiveGrantRules, planViewerUpdates, applyViewerPlan, ALL은 이 레포의 헬퍼

// 부여·회수 함수와 같은 편집 타입 (부여 기록 생성은 타입별, 권한 값 수정은 interface)
type OntologyEdit = Edits.Object<KsGrant> | ViewerEdit;

export default async function resyncKsViewerGroups(client: Client): Promise<OntologyEdit[]> {
    await requireGlobalFunction(client, KS_FUNCTION.grantEdit); // 권한 관리 기능이 있는 사용자만
    const grants = await loadActiveGrantRules(client);
    const batch = createEditBatch<OntologyEdit>(client);
    applyViewerPlan(batch, await planViewerUpdates(client, grants, ALL)); // 바뀌는 객체마다 setViewerGroupIds
    return batch.getEdits();
}
```

이렇게 만든 편집은 `updateObjectForInterface` 형식으로 나갑니다.\
단위 테스트에서는 타입이 다른 객체 두 개(`KsProject`와 `KsGrant`, 둘 다 권한 값을 가진 6개 타입)를 고쳐도 같은 interface 편집 두 개가 나오는지 확인했습니다.

```ts
// __tests__/ksPermissions.test.ts (발췌)

expect(edits.map((e) => e.type)).toEqual(["updateObjectForInterface", "updateObjectForInterface"]);
expect(edits.map((e) => e.obj)).toEqual([
    { $apiName: "KsSecured", $objectType: "KsProject", $primaryKey: "KS-PJ-001" },
    { $apiName: "KsSecured", $objectType: "KsGrant", $primaryKey: "KS-G-001" },
]);
```

문서는 interface를 통한 생성도 설명하지만 interface 속성 중 하나가 기본 키로 구현돼 있어야 한다고 적고 있습니다.\
`KsSecured`에는 그런 속성이 없으므로 생성은 타입별 편집으로 남겼습니다.

### 다른 방법과 비교

| 방법 | 점검 | 쓰기 | 새 권한 타입 추가 | 대가·특징 |
|---|---|---|---|---|
| 타입별 조회·편집 나열 | 타입 수만큼 조회 | 타입별 `Edits.Object` 나열 | 조회·편집 코드와 계산 규칙에 타입 추가 | 코드 중복 |
| TypeScript 제네릭 함수만 | 여전히 타입마다 조회 | 함수 시그니처에 타입별 편집이 남음 | 코드와 계산 규칙에 타입 추가 | 한 번 병합으로 끝나고 새 설정이 없음 |
| Ontology Interface | interface 조회 1번 | `Edits.Interface` 하나<br />생성은 타입별 | interface 구현과 설정, 계산 규칙 추가 | 2단계 병합<br />타입별 설정과 인덱싱<br />병합 뒤 앱 리소스 추가 |

제네릭 함수만으로도 중복은 줄일 수 있고 Foundry 쪽에 새로 늘어나는 것도 없습니다.\
하지만 Foundry가 타입을 묶어 주지 않으므로 조회와 편집 선언은 여전히 타입마다 남습니다.\
interface는 그 묶음을 Ontology 쪽에 두는 대신 아래의 함정을 감수해야 합니다.

## 함정 1: 브랜치에서 만든 interface로 편집하는 함수가 실패했다

이 환경은 모든 Ontology 변경을 Global Branch에서 하고 Proposal로 병합합니다(Main은 보호돼 있습니다).\
그래서 처음에는 Global Branch 하나(`ks-interface-v1`)에 interface 생성과 읽기 코드와 쓰기 코드를 한꺼번에 넣으려고 했습니다.\
읽기는 됐지만 interface로 편집하는 함수가 두 군데서 실패했습니다.

| 어디서 | 증상 |
|---|---|
| 코드 레포 CI의 함수 탐색 (`typescriptDiscoverFunctions`) | `"OntologyEdit" is not a supported type` |
| 브랜치 미리보기 실행 (`rune execute --branch-rid`, Global Branch의 RID 지정) | `Conjure error STATUS 400` (`getObjectTypesForInterfaceTypes`, 오류 문구 그대로) |

오류에 나온 `OntologyEdit`는 함수가 돌려주는 편집 목록의 타입 별칭(`Edits.Object<…> | Edits.Interface<KsSecured>`)입니다.\
별칭 이름이 문제가 아니라 그 안의 interface 편집을 탐색이 해석하지 못한 것이었습니다.

CI 쪽 원인은 확인했습니다.\
CI의 함수 탐색은 빌드가 만든 `build/entityMetadataMapping.json`의 `interfaceTypes` 목록에서 interface를 찾습니다.\
그런데 브랜치에서만 존재하는 interface는 브랜치 CI에서도 이 목록에 들어가지 않았습니다.\
로컬에서 같은 탐색 도구에 이 목록을 넘기면서 interface 한 줄을 직접 넣어 주자 탐색이 통과했습니다.

실행 쪽은 오류 위치로 미루어 런타임이 interface 구현 정보를 브랜치 없이 조회하는 것으로 보입니다.\
functions runtime 0.351과 0.357에서 모두 같았습니다.

더 헷갈렸던 점은 **로컬 `./rune discover`는 통과했다**는 것입니다.\
로컬 rune은 브랜치 기준으로 만든 SDK 메타데이터를 써서 interface를 찾았습니다.\
로컬 통과가 CI 통과를 뜻하지 않았으므로 CI와 같은 확인은 Gradle 빌드로 `build/entityMetadataMapping.json`을 만든 뒤 레포 루트에서 탐색 도구를 직접 돌려서 했습니다.

```bash
typescript-functions/node_modules/.bin/discovery discoverOsdkFunctions "$PWD" out.json \
  --entityMetadataMappingFilePath typescript-functions/build/entityMetadataMapping.json
```

기존 interface에 브랜치에서 구현 타입이나 속성을 새로 추가하는 경우는 시험하지 않았습니다.

### 해결: 2단계 병합

interface 조회는 브랜치에서도 됐으므로 작업을 두 번의 병합으로 나눴습니다.

1. **1단계 브랜치 `ks-interface-v1`**: interface 정의와 6개 타입의 구현, 읽기 함수, 툴체인 업그레이드만 넣습니다.\
   쓰기는 타입별 편집 그대로 두고 병합합니다.
2. **2단계 브랜치 `ks-interface-v2`**: interface가 Main에 있는 상태에서 쓰기 코드를 interface 편집으로 바꿉니다.\
   CI가 통과하는지 확인하고 병합합니다.

1단계를 병합해도 Main의 동작은 바뀌지 않았습니다.\
함수 Action은 Rules에서 지정한 함수 버전을 쓰고 자동 업그레이드를 켜면 호환되는 Minor·Patch 버전까지 따라갑니다([문서](https://www.palantir.com/docs/foundry/action-types/function-actions-getting-started)).\
이 환경의 Main Action은 부여·회수가 2.0.1, 백필이 2.2.0을 가리켰고 자동 업그레이드는 꺼져 있었습니다.\
이 환경에서 Rules에 보이는 버전 하나는 Ontology Manager의 저장 변경 내역으로 보면 그 패치 하나만 받아들이는 범위였으므로 새로 생긴 2.3.0을 쓰지 않았습니다.\
자동 업그레이드를 켜 두었다면 병합 즉시 Main Action이 새 함수를 쓸 수 있으므로 병합 전에 확인해야 합니다.

## 함정 2: 구현 타입마다 Enable interface actions를 켜야 했다

2단계 브랜치에서 CI는 통과했고 브랜치 미리보기 실행도 성공했습니다.\
그런데 브랜치 테스트에서 권한 부여 Action이 실패했습니다.

```text
ApplyActionFailed
Actions:FunctionEditsInterfaceActionsDisabledObjectTypes
```

오류 메시지는 함수가 interface locator로 객체를 편집하는데 대상 오브젝트 타입들이 interface actions를 꺼 두었다는 내용이었습니다.

원인은 오브젝트 타입마다 있는 설정이었습니다.\
Ontology Manager에서 오브젝트 타입을 열고 *Interfaces* 탭의 *Interface action control*에서 *Enable interface actions*를 켜야 합니다.\
이 검증 환경에서는 6개 타입 모두 꺼져 있었습니다.\
켜면 interface Action 타입의 제출 조건이 구현 타입 전부에 똑같이 적용된다는 경고가 함께 나옵니다.

<a href={objectTypeInterfacesTab.src}><Image src={objectTypeInterfacesTab} alt="오브젝트 타입 Ks Grant의 Interfaces 탭. Viewer Group Ids가 Viewer Group Ids로 채워져 있고 Interface action control에 Enable interface actions 토글이 켜져 있다" /></a>
<figcaption>오브젝트 타입 → Interfaces 탭입니다.<br />위는 interface 속성을 기존 속성으로 채운 모습(<em>Fulfilled by</em>)이고 아래가 <em>Enable interface actions</em> 토글과 경고입니다.</figcaption>

공식 문서는 interface Action 타입의 제출 조건과 권한이 구현 타입 전부에 같게 적용되고 *Interface action control*에서 타입별로 끌 수 있다고 설명합니다([문서](https://www.palantir.com/docs/foundry/action-types/actions-on-interfaces)).\
같은 문서는 interface Action 타입을 함수와 함께 쓸 수 없다고도 적고 있습니다.\
이 글의 Action은 interface Action 타입이 아니라 일반 함수 기반 Action입니다.\
그런데도 이 환경에서는 함수가 interface locator로 편집하자 이 설정에 걸렸습니다.

이 함정을 늦게 발견한 이유는 두 가지입니다.

- 함수 탐색과 CI는 이 설정과 관계없이 통과했습니다.\
  브랜치 미리보기 실행은 Action을 거치지 않고 편집을 적용하지도 않으므로 이 설정을 확인할 수 없었습니다([문서](https://www.palantir.com/docs/foundry/functions/typescript-v2-ontology-edits)).
- 백필 Action은 먼저 통과했습니다.\
  값이 이미 맞아 편집을 하나도 만들지 않았기 때문입니다.\
  이 환경에서는 편집이 0건인 실행이 이 검사에 걸리지 않았습니다.

그래서 테스트는 실제로 값이 바뀌는 부여로 해야 합니다.\
6개 타입에서 설정을 켜고 브랜치에 저장하자 `KsGrant`를 뺀 5개 타입의 브랜치 인덱싱이 시작됐고 인덱싱이 끝난 뒤 테스트가 통과했습니다.\
`KsGrant`는 그보다 앞서 Action을 저장할 때 이미 인덱싱돼 있었습니다.

하나 더 관찰한 점이 있습니다.\
Action을 저장할 때 Foundry가 "인덱싱되지 않은 오브젝트 타입을 수정한다"고 안내한 대상은 함수가 타입별로 편집하는 `KsGrant`뿐이었습니다.\
interface로 편집하는 타입은 그 목록에 나오지 않았으므로 저장 화면만 보고 이 설정을 알아채기는 어려웠습니다.

이 환경에서는 이 설정을 켜야 interface를 거친 권한 값 편집이 적용됐습니다.\
그러므로 이 interface로 권한 값을 쓰는 Action의 제출 조건을 함께 확인하는 것을 권합니다.\
이 환경의 백필 Action은 제출 조건을 어드민 그룹으로 제한했고(부여·회수 Action의 제출 조건은 이 글에서 다루지 않습니다) 부여·회수·백필 함수는 모두 함수 안에서 권한 관리 기능이 있는 사용자인지 다시 확인합니다.\
문서도 interface 권한은 Ontology 역할로 관리되고 interface Action으로 객체를 만들고 고치고 지울 수 있는 사용자를 신중히 검토하라고 안내합니다([interface 문서](https://www.palantir.com/docs/foundry/interfaces/interface-overview), [Action 문서](https://www.palantir.com/docs/foundry/action-types/actions-on-interfaces)).

### 웹 앱 리소스는 병합 뒤에만 추가할 수 있었다

### `VALIDATE_ONLY`와 `returnEdits`를 함께 보내면 400이 났다

웹 앱에서 Action을 검증만 하는 버튼이 400 `InvalidApplyActionOptionCombination`으로 실패했습니다.\
Apply Action API의 `options`에는 `mode`(`VALIDATE_ONLY` 또는 `VALIDATE_AND_EXECUTE`)와 `returnEdits`가 있습니다([문서](https://www.palantir.com/docs/foundry/api/ontologies-v2-resources/actions/apply-action)).\
이 환경에서는 `VALIDATE_ONLY`에 `returnEdits`를 함께 보내면 400이 났으므로 검증만 할 때는 `mode`만 보내도록 고쳤습니다.

## 검증 결과

2단계 스크립트는 여기에 권한 부여·회수·백필 Action 실행과 Main 값이 바뀌지 않았는지도 확인합니다.\

| *Enable interface actions*를 켜고 2차 테스트 | 12/12 통과 |
| 2단계 병합 | 함수 2.4.0 발행 |
| 2단계 병합 뒤 Main 점검 | 7/7 통과 |

Main 점검에서 어드민은 60건(`KsLineItem` 31·`KsRevision` 6·`KsGrant` 5·`KsProject` 4·`KsDocument` 4·`KsRevisionSnapshot` 10)을 보았고 팀 A 사용자는 33건을 보았습니다.\
두 계정 모두 interface 조회와 타입별 조회의 결과가 같았고 권한 값이 빈 객체는 0개였습니다.\
1단계 병합 직후와 같은 숫자라서 쓰기를 interface로 바꾼 뒤에도 권한 값이 달라지지 않았음을 확인했습니다.

2차 브랜치 테스트에서 팀 B에게 프로젝트 하나를 부여하자 부여 기록(`KsGrant`) 1건이 생기고 객체 11개의 `viewerGroupIds`에 팀 B가 더해졌습니다.\
회수하면 객체 12개(위 11개와 부여 기록의 상태)가 바뀌어 시작 값으로 돌아왔습니다.

REST의 `returnEdits` 결과에서는 interface 편집도 실제 타입의 수정으로 보였습니다.\
그래서 편집이 interface를 거쳤는지는 함수 단위 테스트(`updateObjectForInterface`)로 확인했습니다.

## 실무 적용 체크리스트

여러 오브젝트 타입의 권한 속성을 interface로 묶는다면 아래 순서를 권합니다.

**1단계 브랜치**

1. **interface 구현**: 권한 속성이 있는 타입마다 interface를 구현하고 interface 속성을 기존 권한 속성으로 채웁니다.
2. **점검 쿼리**: interface 조회 한 번으로 타입별 객체 수와 권한 값이 빈 객체 수를 세는 점검을 둡니다.\
   어드민으로 실행해야 빈 객체가 보입니다.
3. **쓰기는 그대로**: interface로 편집하는 코드는 아직 넣지 않습니다.
4. **함수 버전 발행과 Action 버전 확인**: 브랜치에서 함수 버전을 발행합니다.\
   Main Action의 버전과 자동 업그레이드 설정이 새 버전을 바로 받아들이지 않는지 확인합니다.

**1단계 병합 뒤**

5. **앱 리소스 추가**: Developer Console 앱이 리소스 제한 모드라면 interface와 관련 Action을 리소스에 추가합니다.

**2단계 브랜치**

6. **쓰기 전환**: 쓰기 코드를 interface 편집으로 바꾸고 CI 탐색이 통과하는지 확인합니다.
7. ***Enable interface actions***: 구현 타입마다 켜고 그 타입들의 브랜치 인덱싱이 끝나기를 기다립니다.
8. **제출 조건 확인**: 권한 값을 쓰는 Action의 제출 조건이 어드민 그룹으로 제한돼 있는지와 interface를 편집할 수 있는 사람을 확인합니다.
9. **Action 버전 변경**: 권한 값을 쓰는 Action의 함수 버전을 새 버전으로 바꿉니다.
10. **값이 실제로 바뀌는 테스트**: 편집이 0건인 실행으로는 설정 누락이 드러나지 않았으므로 실제로 값이 바뀌는 부여·회수로 확인합니다.

**2단계 병합 뒤**

11. **Main 확인**: Main에서 구현 타입의 인덱싱 완료와 *Enable interface actions*와 Action의 함수 버전을 확인하고 점검 쿼리를 다시 돌립니다.\
    Main 인덱싱이 끝나기 전에 부여·회수를 실행하는 경우는 시험하지 않았으므로 확인을 마친 뒤 실행하는 편이 안전합니다.

## 정리

interface는 "같은 칸을 가진 여러 타입"을 Ontology에 선언하는 방법입니다.\
권한 값처럼 여러 타입이 같은 이름과 의미로 갖는 속성이라면 읽기와 쓰기를 한 곳으로 모으는 효과가 큽니다.\
다만 정의와 사용을 한 브랜치에 넣지 말고 구현 타입의 설정과 제출 조건까지 함께 챙겨야 합니다.

권한 타입이 한두 개뿐이라면 두 번의 병합과 타입별 설정이 얻는 것보다 클 수 있습니다.\
interface 구현을 다시 걷어 내는 경우는 시험하지 않았습니다.
