<summary>이 글을 쓰게 된 이유</summary>

실무 Palantir Foundry 프로젝트를 준비하면서 개인 개발자 티어에 작은 검증용 환경(`Keystone PoC`)을 구축해 테스트하고 있습니다.\
본문에 등장하는 `Ks…` 접두사 이름은 모두 이 검증 환경에서 붙인 예시이며 데이터 역시 전부 가상입니다.\
권한 값을 가진 타입 중 4개는 글에서 일반적인 이름으로 바꿔 적었고 스크린샷에서는 그 이름을 가렸습니다.

2026년 10월 16일 새벽부터 낮까지 여러 타입에 흩어져 있던 행 단위 권한 처리 코드를 Ontology Interface 하나로 통합하는 작업을 진행했습니다.\
설계 자체는 단순했지만 브랜치 병합 구조와 숨은 설정 때문에 두 번이나 발목이 잡혔습니다.\
비슷한 구조를 고민하는 분들이 같은 지점에서 시간을 허비하지 않길 바라며 기록을 남깁니다.

</details>

Foundry에서 행 단위 권한(Row-level Security)을 적용하다 보면 권한 제어용 속성을 가진 오브젝트 타입이 금세 여러 개로 늘어납니다.\
제가 구성한 환경에서도 6개의 오브젝트 타입이 저마다 `viewerGroupIds`라는 동일한 이름의 권한 속성을 가지고 있었고 이 값을 점검하거나 수정하는 코드 역시 타입별로 중복해서 작성해야 했습니다.\
이 글에서는 **흩어져 있던 권한 속성을 하나의 Ontology Interface로 묶어 한 곳에서 읽고 쓸 수 있게 리팩터링한 과정**을 공유합니다.

결론부터 말씀드리면 권한 값이 누락된 객체를 찾는 점검 로직은 **Interface 조회 단 한 번**으로 줄어들었고 권한 값을 갱신하는 코드는 더 이상 **대상 객체의 구체적인 타입을 몰라도 되게** 바뀌었습니다.\
앞으로 권한 제어가 필요한 새 오브젝트 타입이 추가되더라도 Interface만 구현하면 즉시 점검 대상에 포함됩니다.\
(물론 '누가 볼 수 있는지' 계산하는 비즈니스 규칙은 여전히 타입마다 정의해야 합니다.)

물론 트레이드오프도 있습니다.\
Foundry 쪽 작업을 **두 번의 병합(Merge) 단계**로 나누어야 했고 구현 타입마다 추가로 켜 주어야 하는 설정도 하나 늘어났습니다.\
게다가 브랜치에서 타입이나 Action을 바꾼 뒤에는 브랜치 인덱싱을 기다려야 했는데 이 환경에서는 Action 저장 후 타입 하나가 인덱싱되는 데만 약 10분이 걸리기도 했습니다.\
또한 이 환경에서는 *Enable interface actions* 설정을 켜야만 Interface 기반 편집이 동작했기 때문에 권한 값을 수정하는 Action의 제출 조건(Submission criteria)도 한층 더 꼼꼼히 점검하는 것이 좋습니다.

무엇보다 작업 과정에서 예상치 못한 **두 가지 함정**을 겪었습니다.

1. **브랜치에서 새로 만든 Interface로 편집하는 함수가 CI와 브랜치 미리보기 실행 모두에서 실패했습니다.**\
   결국 Interface 정의와 읽기 코드만 먼저 Main에 병합한 뒤 다음 브랜치에서 쓰기 코드를 병합하는 2단계 병합으로 우회해야 했습니다.
2. **구현 타입마다 *Enable interface actions* 토글을 켜지 않으면 실제 Action 실행 단계에서 에러가 발생했습니다.**\
   함수 탐색과 CI와 브랜치 미리보기 실행이 모두 통과한 뒤 Action 실행 단계에서야 드러나는 문제라 특히 주의가 필요했습니다.

## 배경: 행 권한이 걸린 6개 오브젝트 타입

본격적인 설명에 앞서 본문에서 자주 쓰이는 Foundry 핵심 용어를 간단히 짚고 넘어가겠습니다.

- **오브젝트 타입(Object type)**: Ontology에서 하나의 업무 대상을 나타내는 타입입니다.\
  데이터베이스 테이블 하나에 대응하는 모델 클래스라고 생각하면 이해하기 쉽습니다.
- **Object Security Policy**: 오브젝트 타입에 적용하는 행 단위 접근 제어 규칙입니다.\
  사용자의 속성(소속 그룹 ID 등)과 객체의 속성을 비교하는 [Granular Policy](https://www.palantir.com/docs/foundry/platform-security-management/manage-granular-policies)를 통해 특정 행의 노출 여부를 결정합니다([공식 문서](https://www.palantir.com/docs/foundry/object-permissioning/object-security-policies)).
- **Action**: Ontology의 객체를 변경하는 표준 작업 단위입니다.\
  이 글에 등장하는 Action은 모두 TypeScript 함수가 변경할 내용(Edits)을 계산해 반환하면 Action이 이를 실제 Ontology에 반영하는 **함수 기반 Action(Function-backed Action)**입니다.
- **Edit-only 속성**: 백킹 데이터셋(Backing dataset)의 컬럼과 연결하지 않고 오직 Ontology 편집(Action 등)으로만 값을 채우는 속성입니다.\
  Object Storage V2 타입에서만 사용할 수 있으며 속성 자체의 권한은 백킹 데이터셋 중 하나를 따릅니다([공식 문서](https://www.palantir.com/docs/foundry/object-link-types/edit-only-properties)).
- **Global Branching**: Ontology 설정과 코드 레포지토리를 하나의 브랜치에서 함께 수정하고 Proposal을 통해 기본 브랜치로 병합하는 기능입니다([공식 문서](https://www.palantir.com/docs/foundry/global-branching/core-concepts)).\
  코드 레포의 기본 브랜치는 `master`, Ontology의 기본 브랜치는 `Main`으로 부릅니다.
- **브랜치 인덱싱(Branch indexing)**: 브랜치에서 정의를 변경하거나 Action으로 수정하려는 오브젝트 타입을 해당 브랜치에서 조회·편집할 수 있도록 색인하는 작업입니다.\
  테스트 환경에서는 인덱싱이 완료되기 전까지 해당 타입을 수정하는 Action을 브랜치에서 실행할 수 없었습니다.
- **OSDK와 `rune`**: [OSDK(Ontology SDK)](https://www.palantir.com/docs/foundry/ontology-sdk/typescript-osdk)는 Ontology 정의로부터 생성한 타입으로 객체를 다루는 TypeScript SDK입니다.\
  `rune`은 이 환경의 TypeScript Functions 레포 템플릿에 포함된 CLI 도구로 로컬에서 함수를 탐색(Discovery)하고 테스트 실행할 때 사용했습니다.
- **함수 탐색(Discovery)**: 함수 레포를 빌드할 때 어떤 함수가 정의되어 있고 각 함수가 어떤 오브젝트 타입을 읽고 수정하는지 분석해 메타데이터로 등록하는 단계입니다.
- **백필(Backfill)**: 비어 있거나 어긋난 권한 값을 권한 규칙에 맞춰 일괄 재계산해 채워 넣는 작업입니다.

검증 환경의 행 단위 권한 대상은 아래 6개 타입이며 모든 타입이 `viewerGroupIds`(배열)라는 그룹 ID 목록 속성을 공통으로 가집니다.

| 타입 | 설명 |
|---|---|
| `KsProject` | 프로젝트 |
| `KsDocument` | 프로젝트 산하의 문서 |
| `KsRevision` | 문서의 작업본·리비전 |
| `KsRevisionSnapshot` | 리비전에 속한 참조 사본 |
| `KsLineItem` | 세부 항목 |
| `KsGrant` | 권한 부여 기록 |

각 타입에 설정된 Object Security Policy는 **사용자가 속한 그룹과 객체의 `viewerGroupIds`가 하나라도 겹치거나 사용자가 관리자 그룹(`ks-app-admin`)에 속해 있을 때만** 해당 행을 보여 줍니다.

여기서 `viewerGroupIds`는 **Edit-only 속성**으로 설계했습니다.\
파이프라인(Transform)이 데이터셋을 다시 빌드하더라도 기존에 부여된 권한 값이 덮어써지지 않도록 보호하기 위해서입니다.

대신 한 가지 신경 써야 할 점이 생깁니다.\
Transform이 새로운 행을 만들어 내면 처음에는 `viewerGroupIds`가 비어 있는(`null`) 상태가 되어 일반 사용자에게는 보이지 않습니다.\
따라서 객체가 생성된 뒤 Action을 통해 권한 값을 채워 넣어야 합니다(Automate로 자동화하는 방법도 있습니다).\
실무에서도 원천 데이터가 파이프라인으로 유입되는 구조라면 똑같이 겪게 되는 시나리오입니다.

결국 이 구조에서는 다음 두 가지 작업이 끊임없이 반복됩니다.

1. **점검(Audit)**: 6개 타입 전체를 훑으며 `viewerGroupIds`가 비어 있는 객체가 없는지 확인합니다.
2. **쓰기(Mutation)**: 권한 부여·회수·백필 Action이 실행될 때 영향받는 객체들의 `viewerGroupIds`를 갱신합니다.

Interface를 도입하기 전에는 이 두 작업 모두 6개 타입을 일일이 따로 조회하고 타입별 편집 코드를 길게 나열해야 했습니다.

## 설계: `KsSecured` Interface 도입

[Ontology Interface](https://www.palantir.com/docs/foundry/interfaces/interface-overview)는 여러 오브젝트 타입이 공통으로 가지는 형태(속성 구조)를 선언하는 추상 타입입니다.\
Interface 자체로는 인스턴스를 생성할 수 없으며 모든 객체는 항상 이를 구현한 구체적인 오브젝트 타입에 속합니다.\
TypeScript의 `interface`와 비슷한 개념으로 볼 수 있습니다.

설계한 `KsSecured` Interface의 핵심 구조는 다음과 같습니다.

- **`KsSecured` Interface에 `viewerGroupIds` 속성 하나만 선언합니다.**\
  화면 표시 이름은 *Viewer Group Ids*입니다.
- **6개 오브젝트 타입이 모두 `KsSecured`를 구현하도록 연결합니다.**\
  각 오브젝트 타입의 *Interfaces* 탭에서 Interface를 추가하고 Interface의 속성을 각 타입이 기존에 가지고 있던 `viewerGroupIds` 속성과 매핑합니다([공식 문서](https://www.palantir.com/docs/foundry/interfaces/implement-interface)).\
  이 환경에서는 Edit-only 속성인 `viewerGroupIds`도 문제없이 연결할 수 있었습니다(화면에는 *Fulfilled by*로 표시되며 아래 '함정 2' 섹션의 스크린샷 상단에서 확인할 수 있습니다).
- **'누가 볼 수 있는지' 계산하는 비즈니스 로직은 Interface로 합치지 않습니다.**\
  프로젝트는 프로젝트 단위 권한으로, 세부 항목은 프로젝트 및 항목 범위로 계산하는 등 타입마다 권한 산출 규칙이 다르기 때문에 계산 로직은 기존처럼 타입별 함수에 그대로 남겨 두었습니다.

요컨대 Interface는 **"권한 값을 담는 칸이 어디에 있는가"**만 하나로 통일하고 **"그 칸에 어떤 값을 채울 것인가"**는 기존 도메인 로직이 그대로 결정하도록 역할을 분리한 것입니다.

### 읽기: Interface 조회 한 번으로 끝내는 권한 점검

OSDK 클라이언트에 오브젝트 타입 대신 Interface를 넘기면 해당 Interface를 구현한 모든 타입의 객체를 한 번에 조회할 수 있습니다.\
반환된 각 객체가 실제로 어떤 타입인지는 `$objectType` 필드로 구분합니다.\
TypeScript Functions 환경에서는 함수가 `Client` 인스턴스를 인자로 받고 Ontology로부터 자동 생성된 SDK 패키지에서 `KsSecured`를 가져와 바로 호출하면 됩니다.

```ts
// helpers/viewerData.ts (발췌, 패키지 이름은 예시)
import { Client } from "@osdk/client";
import { KsSecured } from "@keystone/sdk";

export async function auditSecuredObjects(client: Client): Promise<Map<string, { total: number; missing: number }>> {
    // asyncIter()는 페이지를 자동으로 넘기며 객체를 순회합니다. Array.fromAsync는 ES2024 런타임 기능입니다.
    const objects = await Array.fromAsync(client(KsSecured).asyncIter());
    const byType = new Map<string, { total: number; missing: number }>();
    objects.forEach((o) => {
        const entry = byType.get(o.$objectType) ?? { total: 0, missing: 0 };
        entry.total += 1;
        if (o.viewerGroupIds == null) entry.missing += 1;
        byType.set(o.$objectType, entry);
    });
    return byType;
}
```

이때 기억해야 할 중요한 특징이 있습니다.\
이 환경에서 **Interface를 통한 조회 결과는 각 오브젝트 타입의 Object Security Policy를 거친 타입별 조회 결과와 같았습니다.**\
공식 문서도 사용자는 권한 없는 객체와 속성 값을 읽을 수 없다고 설명합니다([공식 문서](https://www.palantir.com/docs/foundry/object-permissioning/object-security-policies)).\
`viewerGroupIds`가 비어 있는 객체는 오직 관리자 그룹(`ks-app-admin`) 조건으로만 조회되므로 **누락 점검 함수는 관리자 권한으로 실행해야** 정확한 결과를 얻을 수 있습니다.\
일반 사용자 계정으로 실행하면 권한 값이 비어 있는 객체 자체가 아예 조회되지 않아 누락 건수가 항상 `0`으로 나오게 됩니다.

또한 위 코드는 전체 객체를 읽어 와서 메모리에서 카운트하므로 대상 객체가 많아지면 그만큼 오래 걸립니다.\
[Interfaces 공식 문서](https://www.palantir.com/docs/foundry/interfaces/interface-overview)에도 Interface 기준 집계(Aggregation) 기능은 아직 개발 중으로 적혀 있습니다.

검증을 위해 React 웹 앱에도 동일한 조회 로직을 붙여 Interface 통합 조회 결과와 6개 타입 개별 조회 결과를 나란히 비교해 보았습니다.

### 쓰기: 구체적인 타입을 몰라도 되는 편집

[TypeScript Functions v2](https://www.palantir.com/docs/foundry/functions/typescript-v2-ontology-edits)는 기존의 `Edits.Object`뿐만 아니라 `Edits.Interface` 타입을 지원해 Interface를 통한 속성 수정을 허용합니다.\
함수 안에서 `createEditBatch`로 배치 인스턴스를 생성한 뒤 수정 사항을 담고 `batch.getEdits()`를 반환하면 이를 호출한 Action이 실제 Ontology에 변경 사항을 반영하는 흐름입니다.

공식 문서의 예제는 Interface로 조회한 객체 인스턴스를 그대로 `batch.update()`에 넘기도록 안내합니다.\
하지만 제 코드에서는 권한 계산을 위해 이미 타입별로 조회해 둔 객체들을 재사용해야 했기 때문에 Interface 이름(`$apiName`)과 실제 오브젝트 타입(`$objectType`)과 기본 키(`$primaryKey`)를 조합해 **Interface Locator 객체**를 직접 만들어 넘기는 방식을 택했습니다.\
(이 Locator 구조는 공식 문서에 명시되어 있지 않아 이 환경의 코드와 단위 테스트로 직접 확인했습니다.)

```ts
// helpers/viewerData.ts (발췌)
import { Osdk } from "@osdk/client";
import { EditBatch, Edits } from "@osdk/functions";
import { KsSecured } from "@keystone/sdk";

export type ViewerEdit = Edits.Interface<KsSecured>;

/** viewerGroupIds를 가진 객체의 공통 인터페이스 (6개 타입 공통 구조) */
export interface SecuredObject {
    readonly $apiName: string;
    readonly $primaryKey: string;
    readonly viewerGroupIds?: readonly string[];
}

/** 함수마다 다른 편집 타입과 조합해 쓰므로 update 메서드만 요구합니다 */
type ViewerEditSink = Pick<EditBatch<ViewerEdit>, "update">;

export function securedRef(object: SecuredObject) {
    return {
        $apiName: KsSecured.apiName,
        // 구현하지 않은 타입을 넘겨도 타입 단언 때문에 컴파일은 통과하므로 호출부에서 6개 구현 타입만 넘기도록 주의합니다
        $objectType: object.$apiName as Osdk.Instance<KsSecured>["$objectType"],
        $primaryKey: object.$primaryKey,
    };
}

export function setViewerGroupIds(batch: ViewerEditSink, object: SecuredObject, viewerGroupIds: string[]): void {
    batch.update(securedRef(object), { viewerGroupIds });
}
```

이 헬퍼를 활용하면 백필 함수(`resyncKsViewerGroups`)가 훨씬 깔끔해집니다.\
누가 어떤 객체를 볼 수 있는지 계산하는 단계(`planViewerUpdates`)는 기존의 타입별 규칙을 그대로 따르고 계산된 결과를 실제로 반영하는 단계(`applyViewerPlan`)만 단일 Interface 편집으로 처리합니다.

```ts
// functions/resyncKsViewerGroups.ts (발췌)
import { Client } from "@osdk/client";
import { createEditBatch, Edits } from "@osdk/functions";
import { KsGrant } from "@keystone/sdk";
// ViewerEdit, requireGlobalFunction, KS_FUNCTION, loadActiveGrantRules, planViewerUpdates, applyViewerPlan, ALL은 레포 내부 헬퍼입니다

// 부여·회수 함수와 동일한 편집 유니온 타입 (권한 부여 기록 생성은 타입별 편집, 권한 값 갱신은 Interface 편집)
type OntologyEdit = Edits.Object<KsGrant> | ViewerEdit;

export default async function resyncKsViewerGroups(client: Client): Promise<OntologyEdit[]> {
    await requireGlobalFunction(client, KS_FUNCTION.grantEdit); // 권한 관리 기능이 있는 사용자만 실행 가능
    const grants = await loadActiveGrantRules(client);
    const batch = createEditBatch<OntologyEdit>(client);
    applyViewerPlan(batch, await planViewerUpdates(client, grants, ALL)); // 변경된 객체마다 setViewerGroupIds 호출
    return batch.getEdits();
}
```

이렇게 만든 편집은 `updateObjectForInterface` 형식으로 나갑니다.\
단위 테스트에서는 서로 다른 두 타입(`KsProject`와 `KsGrant`)의 객체를 수정하더라도 동일한 `updateObjectForInterface` 편집 두 개가 생성되는 것을 확인했습니다.

```ts
// __tests__/ksPermissions.test.ts (발췌)
// edits = 백필 함수가 반환한 편집 목록
expect(edits.map((e) => e.type)).toEqual(["updateObjectForInterface", "updateObjectForInterface"]);
expect(edits.map((e) => e.obj)).toEqual([
    { $apiName: "KsSecured", $objectType: "KsProject", $primaryKey: "KS-PJ-001" },
    { $apiName: "KsSecured", $objectType: "KsGrant", $primaryKey: "KS-G-001" },
]);
```

참고로 공식 문서에는 Interface를 통한 객체 생성(`create`)도 소개되어 있지만 이를 사용하려면 Interface 속성 중 하나가 기본 키(Primary Key)로 매핑되어 있어야 합니다.\
`KsSecured`는 `viewerGroupIds` 하나만 가지는 구조이므로 객체 생성은 기존처럼 구체 타입별 편집(`Edits.Object`)으로 유지했습니다.

### 접근 방식 비교: 타입별 나열 vs 제네릭 vs Ontology Interface

| 접근 방식 | 누락 점검(읽기) | 권한 갱신(쓰기) | 새 권한 대상 타입 추가 시 | 특징 및 비용 |
|---|---|---|---|---|
| **타입별 조회·편집 나열** | 타입 수만큼 개별 조회 | 타입별 `Edits.Object` 나열 | 조회·편집 코드와 계산 규칙 모두에 타입 추가 | 가장 단순하지만 코드 중복이 심함 |
| **TypeScript 제네릭 함수만 사용** | 여전히 타입마다 개별 조회 | 함수 시그니처에 타입별 편집 유니온이 남음 | 조회·편집 코드와 계산 규칙에 타입 추가 | 1회 병합으로 끝나고 추가 플랫폼 설정이 필요 없음 |
| **Ontology Interface 도입** | **Interface 조회 1번으로 통합** | **`Edits.Interface` 하나로 통일**<br />(객체 생성은 타입별 유지) | Interface 구현 연결 + 설정 활성화 + 계산 규칙 추가 | 2단계 병합 필요<br />타입별 설정·인덱싱 대기<br />병합 후 앱 리소스 등록 필요 |

단순히 코드 중복만 줄이는 것이 목표라면 TypeScript 제네릭 함수만으로도 상당 부분 해결할 수 있고 Foundry 설정을 건드릴 필요도 없습니다.\
하지만 플랫폼 차원에서 타입들을 하나로 묶어 주지 않기 때문에 전체 점검 조회나 함수 반환 타입 선언에서는 여전히 모든 타입을 나열해야 합니다.\
반면 Ontology Interface는 그 묶음을 플랫폼 계층에 선언하는 대신 지금부터 설명할 두 가지 함정을 넘어야 합니다.

## 함정 1: 브랜치에서 새로 만든 Interface로 편집하는 함수가 실패했다

제 작업 환경은 모든 Ontology 변경을 Global Branch에서 작업한 뒤 Proposal로 병합합니다(`Main` 브랜치는 보호되어 있습니다).\
그래서 처음에는 단일 브랜치(`ks-interface-v1`) 안에서 `KsSecured` Interface를 새로 만들고 읽기 코드와 쓰기 코드까지 한꺼번에 넣어 병합하려 했습니다.

그런데 읽기 코드는 정상 동작했지만 **Interface를 통해 편집(`Edits.Interface`)하는 함수가 두 군데에서 실패**했습니다.

| 실패 지점 | 에러 메시지 및 증상 |
|---|---|
| 코드 레포 CI의 함수 탐색 단계 (`typescriptDiscoverFunctions`) | `"OntologyEdit" is not a supported type` |
| 브랜치 미리보기 실행 (`rune execute --branch-rid <Global Branch RID>`) | `Conjure error STATUS 400` (`getObjectTypesForInterfaceTypes`) |

첫 번째 에러 메시지에 등장한 `OntologyEdit`는 함수가 반환하는 편집 목록의 타입 별칭(`Edits.Object<…> | Edits.Interface<KsSecured>`)입니다.\
타입 별칭 이름 자체가 문제였던 것이 아니라 그 안에 포함된 `Edits.Interface<KsSecured>`를 CI 함수 탐색기가 해석하지 못해 발생한 에러였습니다.

원인을 추적해 보니 다음과 같았습니다.

- **CI 함수 탐색 실패 원인**: CI의 함수 탐색 단계는 빌드 과정에서 생성되는 `build/entityMetadataMapping.json` 파일의 `interfaceTypes` 목록에서 Interface 정보를 찾습니다.\
  그런데 **아직 Main에 병합되지 않고 브랜치에만 존재하는 신규 Interface는 브랜치 CI 빌드에서도 이 목록에 포함되지 않았습니다.**\
  실제로 로컬에서 해당 JSON 파일에 `KsSecured` 항목 한 줄을 수동으로 추가한 뒤 탐색 도구를 실행해 보니 정상적으로 통과했습니다.
- **미리보기 실행 400 에러 원인**: 에러가 발생한 API 이름(`getObjectTypesForInterfaceTypes`)으로 미루어 볼 때 함수 런타임이 Interface의 구현 타입 목록을 브랜치 정보 없이 조회하는 것으로 보입니다.\
  이 현상은 `functions runtime` 0.351과 0.357 버전 모두에서 동일하게 재현되었습니다.

더욱 헷갈렸던 점은 **로컬에서 실행한 `./rune discover` 명령은 아무 에러 없이 통과했다**는 사실입니다.\
로컬 `rune` CLI는 브랜치 기준으로 생성된 SDK 메타데이터를 참조해 Interface를 인식했기 때문입니다.\
즉 로컬 `rune discover` 통과가 곧 CI 통과를 뜻하지 않았으므로 이 환경에서는 Gradle 빌드로 `build/entityMetadataMapping.json`을 생성한 뒤 레포 루트에서 탐색 도구를 직접 실행해 CI와 같은 조건으로 확인했습니다.

```bash
typescript-functions/node_modules/.bin/discovery discoverOsdkFunctions "$PWD" out.json \
  --entityMetadataMappingFilePath typescript-functions/build/entityMetadataMapping.json
```

*(참고: 이미 Main에 존재하는 Interface에 브랜치에서 새 구현 타입이나 속성을 추가하는 경우는 별도로 테스트하지 않았습니다.)*

### 해결책: 2단계 병합(Two-stage Merge)으로 분리

Interface를 통한 조회(읽기)는 브랜치에서도 문제없이 동작했기 때문에 작업을 두 번의 병합으로 나누어 해결했습니다.

1. **1단계 브랜치 (`ks-interface-v1`)**: `KsSecured` Interface 정의와 6개 오브젝트 타입의 Interface 구현 연결, 읽기(점검) 함수, 툴체인 업그레이드만 포함합니다.\
   쓰기 코드는 기존의 타입별 편집(`Edits.Object`) 그대로 유지한 채 먼저 Main에 병합합니다.
2. **2단계 브랜치 (`ks-interface-v2`)**: 이제 `KsSecured` Interface가 Main에 정식으로 존재하므로 쓰기 코드를 `Edits.Interface` 기반으로 교체합니다.\
   CI 통과를 확인한 뒤 병합을 완료합니다.

1단계를 Main에 병합한 뒤 2단계 브랜치를 열자 로컬 Gradle 빌드가 생성한 `entityMetadataMapping.json`에 드디어 `KsSecured`가 포함되었고 CI도 깔끔하게 통과했습니다.\
1단계에서 400 에러를 뱉던 브랜치 미리보기 실행 역시 정상 동작했습니다.

또한 1단계를 병합하는 동안 기존 Main 환경의 Action 동작에는 아무런 영향이 없었습니다.\
[함수 기반 Action](https://www.palantir.com/docs/foundry/action-types/function-actions-getting-started)은 Rules 탭에 지정된 함수 버전을 사용하며 자동 업그레이드(Auto upgrade) 옵션을 켰을 때 호환되는 Minor·Patch 버전을 자동으로 따라갑니다.\
제 환경에서는 Main의 부여·회수 Action이 `2.0.1`을, 백필 Action이 `2.2.0`을 고정으로 가리키고 있었고(저장 내용상 그 패치 하나만 받는 범위) 자동 업그레이드도 꺼져 있었기 때문에 1단계 병합으로 `2.3.0` 함수가 발행되어도 기존 Action은 영향을 받지 않았습니다.\
만약 자동 업그레이드를 켜 두었다면 병합 즉시 새 함수 버전이 적용될 수 있으므로 사전에 꼭 확인해야 합니다.

## 함정 2: 구현 타입마다 'Enable interface actions'를 켜야 했다

2단계 브랜치에서 CI도 통과하고 브랜치 미리보기 실행도 성공했으니 다 끝났다고 생각했습니다.\
그런데 실제 브랜치 테스트에서 권한 부여 Action을 실행하자마자 아래와 같은 에러가 발생하며 실패했습니다.

```text
ApplyActionFailed
Actions:FunctionEditsInterfaceActionsDisabledObjectTypes
```

함수가 Interface Locator를 사용해 객체를 수정하려 했지만 대상 오브젝트 타입들에서 Interface Action 허용 설정이 꺼져 있다는 메시지였습니다.

원인은 각 오브젝트 타입에 숨어 있는 토글 설정 하나였습니다.\
Ontology Manager에서 대상 오브젝트 타입을 열고 **Interfaces 탭 → Interface action control** 섹션에 있는 ***Enable interface actions*** 토글을 켜 주어야 합니다.\
검증 환경의 6개 타입 모두 기본값으로 이 옵션이 꺼져 있었습니다.\
토글을 켜면 "Interface Action 타입의 제출 조건(Submission criteria)이 모든 구현 타입에 동일하게 적용된다"는 안내 문구가 함께 표시됩니다.

여기서 [공식 문서](https://www.palantir.com/docs/foundry/action-types/actions-on-interfaces)의 설명과 이 환경에서 본 동작을 나란히 놓으면 헷갈리는 부분이 있습니다.\
공식 문서는 Interface Action 타입의 제출 조건과 권한이 구현 타입 전체에 동일하게 적용되며 *Interface action control*에서 타입별로 이를 비활성화할 수 있다고 설명합니다.\
그러면서 동시에 Interface Action 타입은 함수(Function)와 함께 사용할 수 없다고 명시하고 있습니다.

제가 만든 Action들은 Interface Action 타입이 아니라 **일반 함수 기반 Action**입니다.\
그럼에도 이 환경에서는 **함수 내부에서 Interface Locator(`Edits.Interface`)로 객체를 편집하자 Action 실행 시 이 설정(*Enable interface actions*)에 걸렸습니다.**

이 함정을 뒤늦게 발견한 데는 두 가지 이유가 있었습니다.

- **함수 탐색과 CI와 브랜치 미리보기 실행에서는 이 설정에 걸리지 않았습니다.**\
  미리보기 실행은 Action을 거치지 않고 편집을 실제로 적용하지도 않기 때문에 이 설정을 확인할 수 없었습니다([공식 문서](https://www.palantir.com/docs/foundry/functions/typescript-v2-ontology-edits)).
- **앞서 실행한 백필 Action 테스트는 설정이 꺼진 상태에서도 통과했습니다.**\
  당시 모든 객체의 권한 값이 이미 정상이어서 백필 함수가 반환한 편집 목록이 **0건**이었기 때문입니다.\
  이 환경에서는 편집이 0건인 실행이 이 검사에 걸리지 않았습니다.

따라서 테스트는 **실제로 객체 값이 변경되는 시나리오(권한 부여·회수)**로 해야 합니다.\
6개 타입 모두에서 *Enable interface actions*를 켜고 브랜치에 저장하자 이미 인덱싱되어 있던 `KsGrant`를 제외한 나머지 5개 타입의 브랜치 인덱싱이 시작되었고 인덱싱이 완료된 뒤에야 부여·회수 테스트가 모두 통과했습니다.

한 가지 더 덧붙이자면 Action을 저장할 때 Foundry가 "아직 인덱싱되지 않은 오브젝트 타입을 수정합니다"라고 알려 준 대상에는 함수가 구체 타입(`Edits.Object`)으로 직접 수정하는 `KsGrant`만 표시되었습니다.\
`Edits.Interface`로 수정하는 나머지 5개 타입은 경고 목록에 나타나지 않아서 저장 화면만 보고서는 이 설정이나 인덱싱 필요성을 미리 알아채기 어려웠습니다.

결과적으로 이 환경에서는 Interface 기반 편집을 쓰려면 구현 타입마다 이 토글을 켜야 했으므로 **해당 Interface로 권한 값을 수정하는 모든 Action의 제출 조건(Submission criteria)과 권한을 함께 점검**하는 것이 안전합니다.\
제 환경에서는 백필 Action의 제출 조건을 관리자 그룹으로 제한했고 부여·회수·백필 함수 내부에서도 호출자가 권한 관리 권한을 가진 사용자인지 한 번 더 검증하도록 이중 장치를 두었습니다(부여·회수 Action의 제출 조건은 이 글에서 다루지 않습니다).\
공식 문서도 Interface 권한은 Ontology 역할로 관리되며 Interface Action으로 객체를 만들고 수정하고 삭제할 수 있는 사용자를 신중히 검토하라고 안내합니다([Interface 공식 문서](https://www.palantir.com/docs/foundry/interfaces/interface-overview), [Action 공식 문서](https://www.palantir.com/docs/foundry/action-types/actions-on-interfaces)).

### 2. Developer Console의 웹 앱 리소스는 Main 병합 후에만 추가할 수 있었다

제한 모드 앱은 Developer Console의 Ontology SDK 탭에 명시적으로 등록한 오브젝트 타입과 Interface와 Action에만 접근할 수 있습니다([공식 문서](https://www.palantir.com/docs/foundry/developer-console/application-restrictions)).

### 3. `VALIDATE_ONLY` 모드와 `returnEdits` 옵션을 함께 보내면 400 에러가 발생했다

웹 앱에 구현해 둔 'Action 사전 검증(Dry-run)' 버튼을 누르자 `400 InvalidApplyActionOptionCombination` 에러가 반환되었습니다.\
[Apply Action API](https://www.palantir.com/docs/foundry/api/ontologies-v2-resources/actions/apply-action)의 `options` 파라미터에는 실행 방식을 정하는 `mode`(`VALIDATE_ONLY` 또는 `VALIDATE_AND_EXECUTE`)와 편집 내역 반환 여부를 정하는 `returnEdits`가 있습니다.\
검증 환경에서는 `mode: "VALIDATE_ONLY"`와 `returnEdits`를 동시에 전달하면 옵션 조합 오류로 거부되었습니다.\
사전 검증 요청 시에는 `returnEdits`를 빼고 `mode`만 넘기도록 수정해 해결했습니다.

## 최종 검증 결과

변경 전후의 정합성을 확인하기 위해 REST API를 호출하는 Python 검증 스크립트를 작성했습니다.\
동일한 사용자 토큰으로 **Interface를 통해 일괄 조회한 결과**와 **6개 타입을 개별 조회한 결과**(객체 집합 및 각 객체의 `viewerGroupIds` 값)가 완벽히 일치하는지 비교했습니다.\
2단계에서는 권한 부여·회수·백필 Action 실행 결과와 Main 브랜치 영향 여부까지 함께 점검했습니다.

| 검증 단계 | 통과 항목 수 / 전체 항목 수 및 결과 |
|---|---|
| 1단계 브랜치 테스트 | **7 / 7 통과** |
| 1단계 Proposal 병합 | 함수 버전 `2.3.0` 정식 발행 |
| 2단계 브랜치 1차 테스트 | **6 / 10 통과**<br />권한 부여 Action이 '함정 2' 설정 누락으로 실패 |
| *Enable interface actions* 활성화 후 2차 테스트 | **12 / 12 통과** |
| 2단계 Proposal 병합 | 함수 버전 `2.4.0` 정식 발행 |
| 2단계 병합 완료 후 Main 최종 점검 | **7 / 7 통과** |

- **Main 브랜치 정합성 점검**: 관리자 계정은 총 60건(`KsLineItem` 31건, `KsRevisionSnapshot` 10건, `KsRevision` 6건, `KsGrant` 5건, `KsProject` 4건, `KsDocument` 4건)을 조회했고 일반 팀 A 계정은 33건을 조회했습니다.\
  두 계정 모두 Interface 조회 결과와 타입별 개별 조회 결과가 100% 일치했으며 권한 값이 누락된(`null`) 객체는 0건이었습니다.\
  1단계 병합 직후와 수치 변동이 전혀 없어 쓰기 로직을 Interface로 전환한 뒤에도 권한 값이 달라지지 않았음을 확인했습니다.
- **2차 브랜치 부여·회수 테스트**: 팀 B에게 프로젝트 1건의 접근 권한을 부여하자 권한 기록(`KsGrant`) 1건이 새로 생성되고 관련 객체 11개의 `viewerGroupIds`에 팀 B가 추가되었습니다.\
  이어서 권한을 회수하자 총 12개 객체(관련 객체 11개와 권한 기록 상태 변경 1개)가 수정되며 정확히 초기 상태로 복원되었습니다.
- **내부 편집 형식 검증**: 이 환경의 REST API `returnEdits` 응답에서는 Interface를 통한 편집도 구체 오브젝트 타입의 수정으로 보였습니다.\
  따라서 함수가 실제로 Interface 편집 명령(`updateObjectForInterface`)을 생성했는지는 앞서 살펴본 단위 테스트로 검증했습니다.

## 실무 적용을 위한 체크리스트

여러 오브젝트 타입에 흩어진 권한 속성을 Ontology Interface로 통합하려는 분들께 추천하는 적용 순서입니다.

### 1단계 브랜치 (정의 및 읽기 전환)

1. **Interface 정의 및 구현 연결**: 권한 속성을 가진 모든 대상 오브젝트 타입에서 Interface를 구현하고 Interface 속성을 각 타입의 기존 권한 속성과 매핑(*Fulfilled by*)합니다.
2. **통합 점검 쿼리 작성**: Interface 조회 한 번으로 타입별 전체 객체 수와 권한 값 누락 객체 수를 집계하는 점검 함수를 작성합니다.\
   (누락된 객체를 보려면 관리자 권한으로 실행해야 합니다.)
3. **쓰기 로직은 기존 유지**: 아직 Interface가 Main에 없으므로 `Edits.Interface` 기반 쓰기 코드는 넣지 않습니다.
4. **함수 버전 발행 및 Action 설정 확인**: 작업 브랜치에서 새 함수 버전 태그를 발행합니다.\
   이때 Main 브랜치의 기존 Action들이 자동 업그레이드(Auto upgrade)로 인해 새 버전을 바로 쓰지 않는지 미리 확인합니다.

### 1단계 병합 직후

5. **Developer Console 앱 리소스 등록**: 외부 웹 앱이 리소스 제한 모드를 사용 중이라면 Main에 병합된 신규 Interface와 관련 Action들을 앱 허용 리소스에 추가합니다.

### 2단계 브랜치 (쓰기 전환 및 설정 활성화)

6. **쓰기 로직을 Interface 편집으로 전환**: 함수 내 편집 코드를 `Edits.Interface`로 교체하고 CI 함수 탐색이 정상 통과하는지 확인합니다.
7. ***Enable interface actions* 활성화**: Interface를 구현한 모든 오브젝트 타입의 *Interfaces* 탭에서 이 토글을 켜고 대상 타입들의 브랜치 인덱싱이 완료될 때까지 기다립니다.
8. **Action 제출 조건(Submission criteria) 점검**: Interface를 통해 권한 값을 수정하는 모든 Action의 제출 조건이 관리자 그룹으로 제한되어 있는지와 Interface를 편집할 수 있는 사람을 확인합니다.
9. **Action 연결 함수 버전 업데이트**: 관련 Action들이 2단계 브랜치에서 새로 발행한 함수 버전을 가리키도록 변경합니다.
10. **실제 변경이 발생하는 시나리오로 테스트**: 편집 건수가 0건인 실행만으로는 *Enable interface actions* 누락이 드러나지 않았으므로 실제로 객체 값이 바뀌는 권한 부여·회수 시나리오로 테스트합니다.

### 2단계 병합 직후

11. **Main 환경 최종 확인**: Main 브랜치에서 모든 구현 타입의 인덱싱 완료 여부와 *Enable interface actions* 활성화 상태와 Action의 함수 버전을 확인한 뒤 통합 점검 쿼리를 실행합니다.\
    (Main 인덱싱이 끝나기 전에 권한 부여·회수를 실행하는 시나리오는 검증하지 않았으므로 인덱싱 완료를 확인한 뒤 실행하는 것이 안전합니다.)

## 마무리

Ontology Interface는 **"여러 오브젝트 타입이 동일한 의미와 형태의 속성을 공유한다"**는 사실을 플랫폼 수준에서 선언하는 도구입니다.\
행 단위 권한 속성처럼 여러 타입에 똑같이 반복되는 값을 다룰 때 도입하면 읽기와 쓰기 양쪽에서 타입별 분기 코드를 깔끔하게 걷어낼 수 있습니다(계산 규칙과 객체 생성은 타입별로 남습니다).

다만 이 환경에서는 **Interface를 브랜치에서 새로 만들 때 정의와 편집 코드를 두 번의 병합으로 나누어 반영**해야 했다는 점과 **구현 타입마다 *Enable interface actions* 설정과 제출 조건을 꼼꼼히 챙겨야 한다**는 점을 꼭 기억하시기 바랍니다.\
만약 권한 제어 대상 타입이 한두 개뿐이라면 두 번의 병합과 설정 관리 비용이 코드 중복 제거로 얻는 이점보다 클 수 있으니 상황에 맞춰 선택하는 것을 권합니다.\
도입한 Interface 구현을 다시 걷어 내는 경우는 테스트하지 않았습니다.
