AI 코딩 에이전트에게 일을 맡기면 처음 목표와 다른 일을 하고 있는 경우가 자주 있었습니다.\
쓸 수 있는 모델을 고를 수 없는 환경이라서 모델 대신 작업 방식을 바꿔 보기로 했습니다.\
그 방식을 다른 사람도 바로 쓸 수 있게 파일 두 개로 정리했습니다.

</details>

AI 코딩 에이전트에게 일을 맡기면 이런 일이 생깁니다.

- 버그 하나를 고치라고 했는데 주변 코드를 "정리"하기 시작합니다.
- 세 번째 단계쯤 가면 처음 목표를 잊고 다른 문제를 풀고 있습니다.
- 잘못된 방향을 바로잡으려고 대화를 이어 갈수록 더 꼬입니다.

제 경험으로는 대화가 길어질수록 에이전트가 목표를 잃는 일이 잦았습니다.\
이 글은 그 문제를 줄이려고 만든 `GOAL.md` 템플릿과 `AGENTS.md` 규칙을 소개합니다.\
예시는 Codex CLI 기준입니다.\
`AGENTS.md`처럼 저장소의 규칙 파일을 읽는 다른 에이전트에도 같은 방식을 쓸 수 있습니다.

글에서 **세션**은 Codex를 한 번 실행한 단위이고 **대화**는 그 세션 안의 채팅 하나입니다.

## 왜 목표를 잃을까

제가 겪은 경우는 대부분 네 가지 중 하나였습니다.

1. **목표가 대화 안에만 있습니다.**\
   대화가 길어지면 첫 요청은 많은 내용 뒤로 밀립니다.
2. **한 번에 너무 많이 시킵니다.**\
   단계가 많으면 에이전트가 중간에 스스로 일을 만들어 냅니다.
3. **끝이 정해져 있지 않습니다.**\
   언제 끝인지 모르면 에이전트는 무언가를 계속 더 합니다.
4. **범위가 열려 있습니다.**\
   고쳐도 되는 파일이 정해져 있지 않으면 여기저기를 건드립니다.

그래서 이 네 가지를 거꾸로 합니다.\
목표를 **파일로 밖에 두고** 일을 **한 단계씩** 시킵니다.\
그리고 **확인할 수 있는 완료 조건**과 **고정된 범위**를 줍니다.

## 방법 7가지

1. **목표 파일을 둡니다.**\
   `GOAL.md`에 목표 1줄과 완료 조건과 금지 사항을 적습니다.
2. **작게 자릅니다.**\
   요청 하나에 단계 하나만 시키고 끝나면 멈추게 합니다.
3. **계획을 먼저 받고 실행은 나중에 합니다.**\
   계획을 보고 승인한 뒤에 코드를 쓰게 합니다.
4. **완료 조건을 확인할 수 있게 씁니다.**\
   "테스트 X가 통과하면 끝"처럼 씁니다.
5. **범위를 잠급니다.**\
   고쳐도 되는 파일을 정해 둡니다.
6. **목표를 잃으면 새 대화를 엽니다.**\
   `GOAL.md`만 들고 새로 시작합니다.
7. **답마다 목표를 다시 말하게 합니다.**\
   목표를 잃으면 바로 보입니다.

제 경험으로는 1번과 3번의 효과가 가장 컸습니다.\
6번은 사람이 하는 일이고 나머지 6가지는 아래 두 파일에 담았습니다.

## 파일 1: GOAL.md (일마다 하나)

저장소 루트에 둡니다.\
일이 바뀌면 새로 씁니다.\
길어지면 에이전트가 읽을 내용도 늘어나므로 20줄 안쪽으로 씁니다.\
긴 배경 설명은 넣지 않고 필요하면 파일 경로만 적습니다.

섹션 이름(`Goal`, `Done when`, `Scope`, `Do not`, `Steps`, `Now`)은 영어로 두었습니다.\
`AGENTS.md` 규칙에서 같은 이름으로 가리키기 쉽게 하려는 선택입니다.\
내용은 한국어로 써도 됩니다.

```markdown
# GOAL
<!-- 일 하나 = GOAL.md 하나. 20줄 이하. -->

## Goal
<한 문장. 무엇을 할지. 어떻게는 쓰지 않음>

## Done when
- [ ] <실행해서 확인 가능한 조건. 예: `npm test -- cart` 통과>
- [ ] <예: /cart 화면에 합계가 보임>

## Scope
- <고쳐도 되는 파일·폴더 경로>

## Do not
- Scope 밖 파일은 고치지 않는다. (GOAL.md는 예외)
- 새 의존성(dependency)을 추가하지 않는다.
- <이번 일에만 해당하는 금지>

## Steps
1. [ ] <작은 단계>
2. [ ] <작은 단계>
3. [ ] <작은 단계>

## Now
Step: 1
Notes: <1줄. 마지막 결과나 막힌 점>
```

가장 중요한 칸은 `Now`입니다.\
에이전트가 단계를 끝낼 때마다 이 칸을 고치게 합니다.\
그러면 새 대화에서도 이 파일만 읽고 이어서 할 수 있습니다.

## 파일 2: AGENTS.md 규칙 블록 (한 번만)

저장소의 `AGENTS.md`에 붙입니다.\
`AGENTS.md`가 아직 없으면 Codex의 `/init`으로 기본 파일을 만들 수 있습니다.\
Codex는 실행할 때 `AGENTS.md`를 읽어 지시 목록을 만듭니다.\
공식 문서에 따르면 TUI에서는 보통 세션을 시작할 때 한 번 읽습니다.\
그래서 `AGENTS.md`를 고친 뒤에는 Codex를 다시 시작해야 새 규칙이 적용됩니다.

```markdown
## 목표 잠금 (먼저 읽음)
- 파일을 고치는 일이면 매 단계 전에 `GOAL.md`를 읽는다. `GOAL.md`가 없으면 나에게 묻는다. 시작하지 않는다.
- `GOAL.md`의 Steps에서 한 단계만 한다. 그리고 멈추고 기다린다.
- 코드 전에 계획을 쓴다 (고칠 파일, 바꿀 내용, 확인 방법). 내 승인("OK" 또는 plan 승인)을 기다린다.
- Scope에 있는 파일만 고친다. `GOAL.md`는 예외로 고친다. 다른 파일이 필요하면 먼저 묻는다.
- Goal과 Steps에 없는 일은 하지 않는다. 덤 리팩터링 금지. "하는 김에" 금지.
- 단계가 끝나면 `GOAL.md`의 Steps 체크와 Now를 고친다.
- 파일을 고치는 일이면 답의 끝에 2줄을 쓴다:
  `Goal: <Goal 줄 그대로>`
  `Next: <다음 단계 또는 "done">`
- 모르거나 막히면 멈추고 묻는다. 추측하지 않는다.
- Done when의 모든 조건이 통과해야 끝이다. 실행 결과를 보여 준다.
```

첫 규칙과 답 끝 두 줄은 파일을 고치는 일에만 걸리게 했습니다.\
그래야 코드에 대한 질문 같은 가벼운 요청까지 막히지 않습니다.\
`GOAL.md`는 에이전트가 진행 상황을 적는 파일이라서 Scope와 관계없이 고치게 했습니다.

마지막의 두 줄(`Goal:`과 `Next:`)은 경보 장치입니다.\
`Goal:` 줄이 `GOAL.md`와 다르면 에이전트가 이미 목표를 잃은 것입니다.\
긴 답을 다 읽지 않아도 마지막 두 줄로 알 수 있습니다.

### 다른 지시와 부딪칠 때

저장소에 이미 "묻지 말고 끝까지 진행하라" 같은 지시가 있으면 이 규칙과 부딪칩니다.\
Codex는 전역 설정 폴더(`~/.codex`)의 `AGENTS.md`를 먼저 읽고 저장소 루트부터 현재 폴더까지의 `AGENTS.md`를 순서대로 이어 붙입니다.\
그래서 현재 폴더에 가까운 파일의 지시가 뒤에 오고 앞의 지시보다 우선합니다.\
같은 파일 안에서 두 지시가 부딪치면 한쪽을 지우거나 이 규칙이 우선한다고 적어 두기를 권합니다.

### Codex의 `/goal`과 무엇이 다를까

Codex CLI에는 `/goal` 명령도 있습니다.\
공식 문서는 `/goal`이 작업 목표를 설정하고 고치고 멈추고 다시 이어 가게 하며 목표를 현재 대화에 붙여 둔다고 설명합니다.\
`GOAL.md`는 저장소 안의 파일이라서 새 대화에서도 그대로 읽을 수 있습니다.\
그리고 목표 외에 완료 조건과 범위와 진행 상황까지 한곳에 둡니다.\
둘을 함께 쓰려면 `/goal`에 `GOAL.md`의 Goal 줄을 그대로 넣는 방법을 권합니다.

## 쓰는 순서

한 단계는 **계획 → 승인 → 실행 → 멈춤**으로 진행합니다.\
그래서 한 단계에서 두 번 기다립니다.\
한 번은 계획을 승인할 때이고 한 번은 실행 결과를 확인할 때입니다.

1. `GOAL.md`를 채웁니다.\
   Goal, Done when, Scope, Do not, Steps(3\~5개)를 적습니다.
2. Codex에서 `/plan`을 입력해 계획 모드로 바꿉니다.
3. 이렇게 시킵니다: `GOAL.md 읽고 1단계 계획만 써. 코드 쓰지 마.`
4. 계획을 봅니다.\
   맞으면 승인하고 틀리면 이 자리에서 고칩니다.\
   제 경험으로는 방향을 바로잡기 가장 쉬운 시점이 여기였습니다.
5. 단계가 끝나면 답 끝의 두 줄을 확인합니다.
6. 다음 단계를 시킵니다: `GOAL.md 다시 읽고 다음 단계 계획만 써.`\
   계획 모드를 쓰지 않아도 규칙 블록이 코드 전에 계획을 먼저 쓰게 합니다.

## 목표를 잃었을 때

같은 대화에서 고치려고 하지 않습니다.\
제 경험으로는 잘못된 시도가 대화에 남아 있으면 에이전트가 그 방향으로 다시 돌아가는 일이 많았습니다.

1. `GOAL.md`의 `Now`에 1줄을 적습니다.\
   예: `Notes: 2단계에서 Scope 밖 파일을 고침. 되돌림.`
2. `/new`로 새 대화를 엽니다.\
   `/new`는 같은 CLI 세션 안에서 새 대화를 시작합니다.
3. 이렇게 시킵니다: `GOAL.md 읽고 Now부터.`

비슷한 기능으로 `/plan`의 계획을 승인할 때 나오는 **Yes, clear context and implement**가 있습니다.\
공식 문서에 따르면 이 선택지는 완성된 계획을 들고 새 대화를 시작합니다.\
계획만 들고 넘어가므로 `Now`에 적은 진행 상황은 `GOAL.md`에서 다시 읽어야 합니다.

## 복붙용 짧은 명령

| 상황 | 명령 |
|---|---|
| 시작 | `GOAL.md 읽고 1단계 계획만 써. 코드 쓰지 마.` |
| 계속 | `GOAL.md 다시 읽고 다음 단계 계획만 써.` |
| 확인 | `지금 목표와 남은 단계 2줄로.` |
| 범위 벗어남 | `Scope 밖이다. 되돌리고 GOAL.md 다시 읽어.` |

## 설치도 에이전트에게 맡기기

이 글을 에이전트에게 주고 아래 내용을 시켜도 됩니다.

```text
이 글의 "파일 2" 블록을 저장소 AGENTS.md 끝에 추가해.
기존 내용은 바꾸지 마.
그리고 "파일 1" 템플릿을 그대로 루트의 GOAL.md로 만들어.
끝나면 바꾼 파일 목록만 보여 줘.
```

설치가 끝나면 Codex를 다시 시작합니다.\
그래야 새 `AGENTS.md`가 적용됩니다.

## 한국어로 써도 될까

됩니다.\
제가 써 본 환경에서는 Codex가 한국어 지시도 잘 따랐습니다.\
제가 본 바로는 같은 뜻이라도 한국어 문장이 영어보다 토큰을 더 쓰는 경우가 많았습니다.\
규칙 블록이 짧아서 차이는 크지 않습니다.\
섹션 이름과 파일 이름과 답 끝 두 줄의 이름표는 영어로 두었습니다.

## 정리

- 목표를 대화 속에 두지 말고 **`GOAL.md` 파일로 꺼내 둡니다.**
- 한 단계마다 **계획을 먼저 승인**하고 끝나면 멈추게 합니다.
- 답마다 **`Goal:` 줄**을 쓰게 해서 목표를 잃으면 바로 압니다.
- 목표를 잃었으면 고치지 말고 **`/new`로 새로 시작**합니다.

새 기능 설계처럼 더 큰 일이라면 이 방식을 `intent.md → spec.md → plan.md` 세 단계로 늘릴 수 있습니다.\
`GOAL.md`는 그 가벼운 판입니다.
